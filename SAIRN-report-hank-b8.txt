5. ITEM 4 -- A CHAPEL COULD BE PROMISED TO TWO FAMILIES
================================================================================

Found by the hover auditor, H1 batch b25, log seq1370, scanning the
leg_bookings panel. Its override sweep came back CLEAN -- bookingConflict()
hard blocks and there is no override checkbox anywhere -- and the standard scan
then found the real thing:

    bookingConflict() reads only the LOCAL client-side store -- the exact
    TOCTOU race leg_merch_units' reservation-lock was explicitly built to
    close, never applied here.

sairnlegacy.html:2999 is a CORRECT interval-overlap test over bookings(), which
is THIS DEVICE'S localStorage. Two staff on two devices, each holding a copy
taken before the other's booking synced, both pass their own check and both
write -- and the second write is ACCEPTED, because a new booking carries a new
booking_id and nothing collides.

WHAT GETS DOUBLE-BOOKED is a chapel, a removal van, or -- because
leg_facilities seeds FC-3 as {type:'Staff', name:'Maria Chen', notes:'Funeral
Director'} and saveBooking() books Staff rows exactly like rooms -- A NAMED
MEMBER OF STAFF, against a specific death case and a time window.

IT IS NOT THE SAME MECHANISM AS THE MERCH LOCK AND THAT IS STATED RATHER THAN
GLOSSED. tests/sairnlegacy_reservation_lock.js asserts in so many words that
ONE upstream call is the point and that "a read-then-write that happens to
answer 409" is weaker than an atomic conditional PATCH. This gate IS a
read-then-write, because the atomic version is not reachable from here:

  * a conditional PATCH needs an existing row in a known prior state. A new
    booking has no row yet, which is what makes it new.
  * PostgREST has no INSERT ... WHERE NOT EXISTS, so the precondition cannot
    ride on the write.
  * the clean close is a Postgres EXCLUDE constraint over tstzrange, and it
    CANNOT be written against this table as it stands: the window lives in
    `data` jsonb and text::timestamptz is STABLE, not IMMUTABLE, so it is
    rejected in an index expression. It needs real start/end columns or an
    /rpc/ function doing the insert in one statement.

SO WHAT IS AND IS NOT CLOSED, AS A WINDOW RATHER THAN A VERDICT: the
stale-cache race -- minutes to hours wide, the one the auditor found, the one
that actually happens -- is closed, because both devices are now checked
against the SERVER's rows. What remains is two requests interleaving between
the SELECT and the upsert: milliseconds, and it needs two people to click Save
in the same instant.

CANCELLING IS EXEMPT BY DESIGN, and the suite asserts it BY CALL COUNT rather
than by a 200, because a 200 cannot tell an exemption from a check that
happened to pass. cancelBooking() writes the same record with status
'Cancelled', and a gate that refused a cancellation because the booking it is
cancelling overlaps something would be the fix causing the harm.

A WINDOW THAT CANNOT BE READ IS A THIRD STATE. If an existing row's start or
end does not parse, the handler cannot tell whether it clashes, so it REFUSES
with BOOKING_CHECK_INDETERMINATE and names the booking_id -- PR 1.11 applied to
data instead of to a tool. Unreachable from the app today (saveBooking only
ever writes toISOString()), which is exactly why it has to be deliberate: an
unparseable row silently treated as non-overlapping is how this control would
stop working. A real clash still outranks an unreadable one, so "could not
tell" is never reported when the answer is "yes, it clashes".

THE CLIENT HALF IS THE SHARPER HALF. saveBooking() writes to localStorage
BEFORE the await, so the server fix ALONE would have made one thing WORSE: a
refused booking would stay on this device's calendar showing a room the server
knows is not ours -- a silent divergence, where before there was at least a
visible toast. The rollback carries the two properties confirmReserve()'s
rollback was fixed twice to get right, and they are ASSERTED rather than
assumed to have been copied:

  * RE-READ instead of writing back the pre-await snapshot, so a cancellation
    made on this device DURING the request is not silently reverted.
  * only remove the record if it is still OURS and unchanged.
  * a 500 is NOT a refusal -- the local record survives, because deleting a
    merely-unsynced booking is the opposite failure and a worse one.

sdnData() is used here and confirmReserve() deliberately does not use it. That
is not an inconsistency: confirmReserve() was written on 2026-08-10, when
sdnData() collapsed every non-2xx to a bare null and the error code was
unrecoverable. sdnData() has recorded the code per resource since 2026-09-05,
so legLastErrCode() is enough and a second direct-fetch call site -- with its
own copy of the headers, the token and the timeout -- is not worth having.

api/sd-data-leg-bookings-toctou.test.js, NEW -- 48 passed, 0 failed.

PROVEN TO FAIL BEFORE THE FIX, BOTH HALVES SEPARATELY. A test written after the
code it tests is worth nothing until it has been run against the code WITHOUT
