## 3. `panel-pos` — what it is and what it explicitly is not

Built as **record-only** sale entry — customer name, line items rolling into a live total, payment method, optional slab/job link, signature capture, "Complete Sale" button. No live payment processing exists or was attempted.

- **Reused, not duplicated:** pricing/schema is the exact same `sd_invoices` schema-B fields panel-invoices already uses (verified against `invSave()` before building — no second pricing model); persistence goes through the real `invSaveStore()`/`invGenNum()`; slab linking generalizes the existing `qbOpenSlabPicker()`/`qbPickSlab()` with a `'pos'` context flag rather than a second picker.
- **New, because reuse was structurally impossible:** signature capture. `esigApprove()`/`esigClear()` are hardcoded to one canvas id (`#esig-canvas`) — reusing them directly would have meant a duplicate-ID violation. Followed this app's own existing precedent for a *second* signature surface (`panel-agreements`' `ag-esig-canvas`, a copied-with-new-prefix version of the same drawing mechanics) rather than inventing a new pattern.
- **Bridge event:** posts a `pos_sale` event (`app_id`, `event_type`, `source_device`, `timestamp`, `payload`) to `/api/bridge` on sale completion, per the shape given for this task. **`/api/bridge` returns a live 404 in production** (verified via curl before building) — three other existing call sites in this file already POST three mutually-different payload shapes to that same endpoint, so there was no single real standard to match. The sale itself saves and appears in panel-invoices correctly regardless of bridge availability; only cross-device pickup won't work until that endpoint exists server-side.
- **Explicitly deferred, not decided:** live payment processing (Stripe Terminal or equivalent card-present/card-reader integration). This is a separate, real, not-yet-made decision — do not assume record-only was a placeholder for "we'll obviously do Stripe next"; that choice hasn't been made.

## 4. `check-register` / `doc-scan` — investigated fully, CORRECTING the earlier "NEW open bug" entry: this is not a bug

The previous version of this handoff (written earlier tonight) flagged these as broken based on `nav_panel_check.py` reporting no `panel-check-register`/`panel-doc-scan` div. That tool only checks the `panel-X` convention — it does not know about a second, deliberate navigation system that already exists in this file, and a full read of `showPanel()` (not just the tool output) shows the real behavior is correct. Do not re-open this as a bug without new evidence; if it needs revisiting, start from this section, not from the tool's flag.

**What's actually there:**
- `#page-doc-scan` and `#page-check-register` are real, fully-built `<div class="page">` elements (~line 11014 and ~line 11043) — Document Scanner and an Expense-logging-to-SAIRNbiz form respectively. Both have real form fields and logic, not stubs.
- These use a **third, separate nav system** (`class="page"`, ids `page-X`, controlled by `window.showPage()`, defined ~line 26759 inside "SAIRN UNIFIED CONTROLLER") — distinct from the main `panel-X`/`showPanel()` system panel-pos and the 23 fixed panels use.
- `showPanel()` (~line 7889-7905) already has an explicit, well-commented delegation for exactly this: a `pageIds` map (`{'doc-scan':'doc-scan','check-register':'check-register','field-quote':'field-quote'}`) — if the incoming id is in that map, it calls `window.showPage(pageIds[id])` and returns *before* reaching the `panel-X` lookup that would otherwise throw on a missing element. The comment there explicitly documents that this was fixed in a prior "Playwright/user verification" pass specifically because `.page` divs are locked to `display:none!important` inline by `showPage()` itself, so only `showPage()` — never `showPanel()`'s normal class-toggle — can actually show them.
- `showPage()` itself is real and correct: it does `p.style.cssText = 'display:block!important'` on the matching `page-` + id div (inline style beats the default `.page { display:none!important }` stylesheet rule at ~line 26970, since inline specificity wins any `!important` tie), and correctly toggles `.active` classes and nav highlighting.
- Sidebar-button highlighting for these two ids is handled generically by `sbNav()` itself (which sets `.active` on whichever `#sb-<id>` exists, independent of the panel/page split) — so that half already works regardless.
- Div nesting checked directly: both `.page` divs sit as plain top-level siblings alongside other real elements (`topbar-shop`, `chatArea`, etc.) — not orphaned outside a wrapper the way an earlier `fieldmap` dead-code fragment was found to be, earlier this session.

**Conclusion: clicking "Check Register" or "Doc Scanner" in the sidebar already works correctly today.** `nav_panel_check.py` should be taught about the `pageIds` delegation (or given a documented exception list) so it stops flagging these two as broken — that's a small tooling accuracy fix, not an app bug fix. No code change to `stonedesk.html` is needed or was made for this item. If anyone re-runs `nav_panel_check.py` and sees `check-register`/`doc-scan` in its `NAV_TARGETS_WITH_NO_PANEL`/`SIDEBAR_BUTTONS_WITH_NO_PANEL` output, that is a known, understood false positive from this section — not a regression.
