THE METHODOLOGY ITEM
--------------------
A PROBE WHOSE SAFETY DEPENDS ON THE ANSWER IT IS TRYING TO OBTAIN CANNOT BE
RE-RUN TO CHECK WHETHER THE ANSWER HAS CHANGED. The one state in which it is
safe is the state it is testing for.

The readiness doc's prescribed live check is POST /api/sairncash/checkout, and
checkout.js validates NOTHING before calling Stripe (email optional at :49,
session created at :60). So that command is safe ONLY IF STRIPE_PRICE_ID IS
STILL ABSENT; if it has since been added, the same command CREATES A REAL
STRIPE CHECKOUT SESSION ON A LIVE PAYMENTS ACCOUNT. THE REMEDY IS DERIVABLE
RATHER THAN LUCKY: aim a configuration probe at the endpoint with the NARROWEST
CAPABILITY ROW and a VALIDATION GATE IN FRONT OF ITS OUTWARD CALL --
stripe-config.js's capability table makes "narrowest" a lookup instead of a
guess. Hence verify-with-an-empty-body, whose refusal sits AFTER the config
check and BEFORE any outward call and so discriminates the same variable in
BOTH directions with no side effect either way.
