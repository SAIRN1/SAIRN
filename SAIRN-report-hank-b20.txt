3a. sql/sairnlegacy_settings_schema.sql
--------------------------------------------------------------------------------

CONCEPT: one row per home keyed by license_hash, holding b18's two policy
answers as NAMED COLUMNS -- the livery-billing arrangement as text with a
database CHECK on the two-value enum, the apprentice config as jsonb because it
is genuinely a list-of-names shape -- so an invalid value is refused at the
boundary instead of normalised away at read time, and AN ABSENT ROW MEANS THE
NARROW DEFAULT rather than an error.

license_hash is UNIQUE and not merely indexed: two policy rows for one home is
a question with two answers, and whichever a `limit 1` returned would be the
policy. The constraint makes that unrepresentable instead of making the reader
careful.

WHY A CHECK WHEN api/_lib/leg-roles.js ALREADY FAILS NARROW -- the file argues
it rather than assuming it. liveryBilling() SILENTLY REWRITES a bad value to
the default, so a home that stored `direct-to-family` with a hyphen would be
running `through_the_home` and nothing anywhere would say so: they would set
the policy, see no error, and get the other arrangement. The CHECK makes that a
refused write. TWO LAYERS, TWO DIFFERENT FAILURES -- the constraint stops a
wrong value being STORED, the normaliser stops a wrong value being OBEYED if
one ever is.

THE jsonb CHOICE IS THE ONE PLACE THE CONCEPT'S OWN RULE DOES NOT APPLY, so it
is argued: two of the three apprentice fields are LISTS OF RESOURCE NAMES, and
a resource name is not an enum a database can hold in sync with LEG_ROLE_MATRIX
(~36 rows, gaining them in application commits). A membership CHECK would go
stale against the code and start refusing valid configuration. So the
constraint asserts the SHAPE -- object at top level, countersign/forbidden
arrays if present, presence_disclosure boolean if present -- and the comment
says the normaliser remains the authority for membership, typos and the
countersign/forbidden overlap.

NO DELETE IN THE GRANTS, with a reason specific to THIS table rather than
boilerplate: because AN ABSENT ROW MEANS THE NARROW DEFAULT, a TRUNCATE would
revert every home to through_the_home with an empty apprentice config, raise no
error anywhere, and PRESENT AS THE SAFE STATE. A failure that looks like the
safe default is the hardest kind to notice.

THE CROSS-FILE CHECK WAS DRIVEN, NOT ASSERTED. The enum is a SECOND COPY of
LEG_LIVERY_BILLING_VALUES and the apprentice default a second copy of
LEG_APPRENTICE_POLICY_DEFAULT:
  ["through_the_home","direct_to_family"]
  {"countersign":[],"forbidden":[],"presence_disclosure":true,...}
Both agree with the file at this sha. The verification block also carries TWO
NEGATIVE INSERTS -- the hyphenated enum value, and a JSON string where the
object belongs -- each of which MUST ERROR, because a constraint nobody tried
is a constraint nobody has evidence of.

NOTHING READS THIS TABLE YET AND THE FILE'S OWN HEADER SAYS SO. Running it
provisions storage nothing writes to and nothing reads.

3b. THE sairnlaw.html PANEL -- AND THE SPEC WAS WRONG
--------------------------------------------------------------------------------

CONCEPT: one read-only "Needs your authorisation" list in the Trust Accounting
area, rendering ONE NAMED STAGE per row -- the stage the endpoint computes --
because four nullable columns is four chances for a panel to show "signed" for
a spent-and-expired record.

THE CORRECTION IS THE FINDING. b19's routed spec AND the b20 dispatch both say
the panel is "driven by the `status` action" AND that
idx_sairnlaw_countersign_open "exists to serve that query". Those cannot both
be true of what shipped:

  * api/_lib/countersign-endpoint.js:250 -- `status` takes { token } and
    returns ONE row, keyed on token_hash = hashToken(token).
  * the clear token is returned ONCE, at `prepare`, TO THE PREPARER. A signer
    holds no token and could not drive `status` for anything.
  * idx_<app>_countersign_open is (license_hash, resource, expires_at) WHERE
    spent_at IS NULL -- a LIST index. Both SQL files call it "the query a
    director's 'needs your signature' list is built from". NOTHING QUERIED IT.

I wrote one of those two documents myself, one batch earlier. It was found by
reading the endpoint, not by re-reading my own routing note.

SO b20 ADDED `open`, in the shared endpoint, so one implementation serves both
apps. It returns NO TOKEN AND NO TOKEN HASH -- both schemas say why in their own
words: "a readable table of live tokens is a table of signatures waiting to be
borrowed". The panel is therefore READ-ONLY BY CONSTRUCTION, not by politeness;
signing still needs the reference the preparer hands over, which is the
mechanism's design, and the response carries that sentence itself so two apps
cannot grow two wordings of one limitation.

THE STAGE LADDER WAS EXTRACTED, NOT COPIED. stageOf() and STAGE_COLUMNS are one
implementation called by both `status` and `open`. Two copies would be two
answers to "what is this record", and the second would be the one in the list a
signer actually reads. The column list is one string for the same reason: a
column added for one path and not the other would make stageOf read undefined
and compute awaiting_signature for a FILED record.

EXPIRED-BUT-UNSPENT ROWS ARE RETURNED, with the stage saying which they are. A
row that expired unsigned is the one thing a signer most needs to see: an
authorisation that quietly vanished from the list looks exactly like one that
was never prepared, and the preparer is sitting waiting for it.

THE CAP IS REPORTED, NEVER SILENT. Neither token table has a DELETE by design,
so unspent expired rows accumulate without bound. limit = cap+1 is sent purely
to DETECT truncation, and `truncated` is present on BOTH outcomes -- a field
that only appears when truncation happened is a field a client forgets to look
for.

THE PANEL HAS FOUR OUTCOMES AND ONLY ONE MAY SAY "NOTHING WAITING":
  in flight    "Checking with the server..." -- a card headed Needs Your
               Authorisation showing nothing reads as "nothing is waiting"
  503          the lock is not set up on the server -- production TODAY, named
               separately so NOT_PROVISIONED cannot read as "the queue is empty"
  401 / 403    a sign-in answer and a role answer, each its own sentence, each
               stating that it is NOT a statement about what is waiting
  200 + empty  the only place "Nothing waiting" is allowed, and it says the
               answer is the SERVER'S rather than this device's

The panel renders the server's stage and DOES NO ARITHMETIC -- it never reads
countersign_employee_id / countersigned_at / spent_at to decide what a row IS,
because the expiry comparison would be against this device's clock. expires_at
is displayed, never interpreted.

THE ROLE GATE IS UX-ONLY AND IS A SECOND COPY OF A ROLE SET, which this
platform normally refuses -- so the reason it is acceptable is written at the
declaration: it can only ever HIDE. `open` re-checks profile.signerRoles on
every call, so a wider drift still gets refused by the server and a narrower
drift means a signer sees no card and asks.
