4. FOURTH's F4 AND F5 -- F4 FIRST
--------------------------------------------------------------------------

F4, THE DEFECT. The leg_aftercare key was 'AC-'+case_id+'-'+NORMALISED_TYPE.
`-` is BOTH the joiner AND the type normaliser's output character, and
`case_id` went through with trim() alone, so the boundary between the two
fields was not recoverable:

    {case_id:'CS-7',   checkin_type:'1 Week'}  ->  AC-CS-7-1-WEEK
    {case_id:'CS-7-1', checkin_type:'Week'}    ->  AC-CS-7-1-WEEK

The upsert is on_conflict=license_hash,aftercare_id with merge-duplicates, so a
collision SILENTLY OVERWROTE A DIFFERENT CASE'S grief-support check-in and
returned 200.

THE FIX, AND WHY IT IS TWO FORMS RATHER THAN ONE CLEAN ONE. Every row the
shipped app has written has a newId('CS') case id -- ^CS-[0-9]+-[0-9]+$,
sairnlegacy.html:1561 -- with one of three fixed types, and for THAT shape the
boundary IS recoverable: strip a known type suffix, the rest is the case, and
the last case segment cannot contain a `-`. Those pairs keep the HISTORIC key
byte for byte. Everything else takes 'ACX-' plus a reversible escape in which
no segment contains a bare `-` at all. A scheme that moved the historic keys
would ORPHAN EVERY LIVE AFTERCARE ROW: the next write lands on a new row and
the old one is stranded, which is the duplicate the key exists to prevent.

NOT HASHED, and the reason is the whole argument. A hash is shorter and
uniform, and a HASH COLLISION SILENTLY MERGES TWO RECORDS -- this defect with a
smaller probability attached. The escape is reversible, so it cannot collide at
all.

THE GUARD IS ON THE TRIMMED VALUES ON BOTH SIDES NOW. case_id = ' ' passed the
old raw-truthiness guard and trimmed to '', producing a key that collides with
every other whitespace case id -- the exact failure the code's own comment
warns about for a MISSING field, arriving through a present one.

case_id IS DELIBERATELY NOT CASE-FOLDED and arm F4h asserts that as a decision
rather than leaving it to drift. fourth flagged the fold as the same class;
folding only here would make the key say two cases are one while
`a.case_id===caseId` everywhere else in the page says they are two. Whether
case ids should be case-insensitive at all is a product question and is routed,
not answered inside a key derivation.
