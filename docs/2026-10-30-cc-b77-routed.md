## For fourth: sairngrounds.html `grdData()` sends no `app_id`

**What cc b76 changed and b77 reverted.** b76 (`db0bc67a`) changed
`sairngrounds.html` ~:1784 inside `grdData()` from

    body: JSON.stringify({ action: action, resource: resource, payload: payload })

to

    body: JSON.stringify({ action: action, resource: resource, app_id: APP_ID, payload: payload })

b77 reverted it. `sairngrounds.html` is now byte-identical to its state before
b76 (`git diff db0bc67a~1 -- sairngrounds.html` is empty).

**What stays fixed without the client change.** The security half is
server-side and remains in `api/sd-data.js`. For shared and routes resources,
the deleted-row pre-gate now keys on the session token's app
(`preSession.app`), not on `body.app_id`. So a deleted grounds employee is
refused whatever `grdData` sends. `api/b76-shared-deleted-row-session-app.test.js`
proves it: arm `R[rt_routes/read sairngrounds token, app_id ABSENT]` gives
403.

**What the client change is still for.** Without `app_id`, the server treats
every grounds request to a shared or routes resource as `stonedesk` when it
scopes the data. That covers employees, render_usage, rt_routes,
shared_knowledge and employee_profile. A grounds licence then reads and writes
those rows under StoneDesk's app scope. That is a correctness issue, not an
access one.

**Next step for fourth:**
- Add `app_id: APP_ID` to the `grdData` request body, as `sdnData` and
  `alfData` already do.
- Run `node --check` on each script block.
- Confirm the grounds data paths still read their existing rows. If grounds
  rows were written under `stonedesk` before the change, they will need a
  migration decision.
