## 2. The ruling on `tools/hover_auditor_scope_gate.py:409`

Routed by fourth in b10 (in full) and again in b11 (as a register row, because
b10 was still `MENTION_ONLY`). The register row
`2026-10-13-unfetched-base-scope-gate` is owned by cc with state

**`docs/by-design-register.json` IS IN FOURTH'S LIVE b12 FILES, so the ruling is
recorded HERE and not there (PR §4.3, declared and not overridden).** The
`NOT_PROMOTED` half is also in `tools/report_only_checks.py`, which is the
mechanism fourth's routing named and is in no other session's claim.

### 2.1 The fix half: APPLIED

`changed_outgoing()` built its range from `rsha` — the remote's sha, read off
git's pre-push stdin by field position — with no existence test, then reported
the failure as a property of the RANGE. With five sessions pushing one branch
that sha is routinely unfetched: **the ordinary case, reported as an anomaly
about the change.** `_have_commit()` now sits beside `git()`, and an unfetched
remote tip falls back to `merge-base(origin/main, lsha)` with the substitution
stated in the notes, or returns a could-not-read naming `git fetch origin`.

**RE-QUALIFIED FOR THIS TARGET RATHER THAN COPIED** (convention 7): the
merge-base sits further back than the range git asked about, so **more** paths
are examined, never fewer — and for a gate whose job is to REFUSE an
out-of-scope path, a superset can only refuse more. That is the direction that
makes the substitution safe *here*; it is not a property of the pattern.

Driven by `tests/run_scope_gate_unfetched_base_probe.py`, **12/12 arms**,
including **ARM 5, an ablation**: stub `_have_commit` to always answer yes —
which is the pre-fix code exactly — and the same input returns the old opaque
`could not read the outgoing range` refusal. Without that arm, arm 2 could be
passing for some other reason. Regression: `run_hover_separation_probe.py`
**148 passed, 0 failed**; `run_hover_scope_own_claim_probe.py` ALL ARMS PASS.

**The auditor's clone was never entered.** Every arm runs in a throwaway
repository the probe builds.

### 2.2 The checker half: NOT PROMOTED, and the reason is a measurement

The proposed standalone 6-arm static taint checker is **declined**. The
population — `tools/*.py` that parse a pre-push ref line and bind a sha by field
position — is **THREE files**: `hover_auditor_scope_gate.py`,
`register_feed_gate.py`, `sairn_push_gate_hook.py`, **all guarded as of this
run**. A new tool with its own criteria lock, fixtures and six arms, maintained
indefinitely over three already-clean files, buys only the fourth author of the
shape; and fourth named the expensive part itself — arm 3
(`cat-file -e <sha>:<path>`) needs flow-level analysis, and a checker that gets
it wrong **passes the worst real instance while reporting itself clean**.

**The substitute runs instead of being remembered:** arm 6 of the same probe
re-measures that population every run and fails if any member loses its guard;
arm 6b fails if the population ever reads as empty, which is how an arm like
this dies quietly. **Its limit is stated in both places:** the guard is detected
PER FILE, not along the flow — it catches *no guard anywhere*, the shape all four
real instances had, and not *guarded on one path and not another*. That residue
is what was declined; it is not claimed as covered. Promote the full checker if
a fourth instance appears anyway, or if the population passes about six files.

### 2.3 A fifth instance of the same CLASS, hit by this batch, from the other side

`git push` was denied twice at the start of this batch with:

    register_feed_gate: stdin is not a terminal and carried NO ref lines.

This clone was **9 commits behind** at the time. `git pull --rebase origin main`
cleared it and the identical command then pushed. The gate's message offers two
explanations — a wrapper swallowing stdin, or git supplying no refs — and the
session acted on neither, so it is reported as **an observation and NOT a
diagnosis**.

**AND THE OBVIOUS EXPLANATION IS WRONG, which is why it is written down rather
than fixed from a guess.** Later in the same batch this clone was behind AGAIN —
the remote tip `18ed4b0d45d5` was not an object here — and the ref lines arrived
normally; the gate printed its merge-base notice and every check ran. **So
"behind the remote" is not sufficient to produce the no-ref-lines state**, and
whatever is, this batch did not establish it. `register_feed_gate` DID handle
the unfetched tip correctly on those later pushes, which is independent
confirmation that the `:409` fix pattern works where it has been applied.

NOT FIXED HERE and deliberately not bundled: `tools/register_feed_gate.py` is a
push-path gate, this is a second distinct behaviour in it, and the next step is
**a reproduction, not a patch** — nobody should change a push gate on the
strength of two observations and no mechanism. **Routed to whoever next claims
that file**, with both observations above, including the one that rules out the
easy answer.
