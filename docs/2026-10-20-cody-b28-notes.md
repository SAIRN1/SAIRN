## 1. THE CONCEPTS, ONE LINE EACH, BEFORE ANY CODE

| item | the concept |
|---|---|
| **2. rt_routes live** | A landed branch and a deployed branch are different facts, and only a real authenticated request against the real deployment can tell them apart. |
| **3. role-from-token** | A signed token proves WHO ASKED and WHEN THEY SIGNED IN; it cannot prove what they may do NOW, because it was minted before now. **Authentication survives in a token; authorisation does not.** |
| **3b. the settling step** | A deadline re-verifies nothing: if the world may move between the signature and the write, the check at the write must ask about every way it can move — role as well as employment. |
| **4. the payload cap** | A cap belongs where the storage bound is, and two writers of one table with caps twenty times apart means one of them is wrong about the table. |

| **5. the hook at the top** | A fix is not applied until it has EXECUTED, and nothing after a module-level `sys.exit()` executes. |

## 2. THE PATTERN THIS BATCH IS ABOUT

**Three of the four defects were a CORRECT RULE applied one scope too wide, and
in every case the over-wide sentence was written down and believed.**

1. **`MAX_PAYLOAD_BYTES`.** Its comment reasons carefully about `sd_slabs`,
   concludes *"there's no per-resource override at the DB layer, so there can't
   usefully be one here either — this cap stays uniform across every
   resource"*, and is **right about slabs and wrong about the platform**:
   `dnt_appointments` has a per-resource DB override, and so do seven others.
   The sentence was true when written and became a platform-wide claim by
   sitting still.
2. **`MODE_PREPARED_ONLY`.** *"A caller who may FILE the record files it,
   exactly as before this lock existed"* — correct as a policy, and it was
   implemented by trusting the token's role, which is a different statement.
3. **b27's hook placement.** *"The end of the file is the earliest
   registration, so it fires last"* — a careful sentence about the wrong file
   position, reasoning about a line that does not execute.

**The thing that caught all three was DRIVING, never reading.** b27's handoff
said the same about its own three routed items. That is now two consecutive
batches where every defect found was found by running the code.

### 3.4 `sd_locations` runs the other way — the API permits 4× what the DB accepts

`sdlocations_data_size` is **16,384** bytes and the API's default cap is 65,536.
So a 40KB `locations` write is accepted by this file and refused by Postgres,
with the opaque-error outcome the `MAX_PAYLOAD_BYTES` comment records paying for
on slabs — **in the direction that comment did not consider.** A fix here LOWERS
a cap, which can break a working client, so it is a different change with
different risk. Arm C8 asserts `sd_locations` is absent from the cap table so it
cannot be swept in as a seventh.
