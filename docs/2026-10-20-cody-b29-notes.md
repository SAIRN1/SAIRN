## 2. THE PATTERN THIS BATCH IS ABOUT

**Every item turned on knowing which mechanism actually governs the thing —
and in three of five, the obvious answer was wrong in a way that was already
written down somewhere.**

1. **The caps.** b28 pinned "six uncovered oversized tables". **Three of the
   six were never governed by that gate**: `sd_progress_photos` is written by
   `api/sd-sub-data.js`, whose own cap is already 1,572,864;
   `sd_quote_request_photos` by `api/stonedesk-public.js`, whose
   `MAX_PHOTO_CHARS` was sized *from* that row cap and says so. b28's error was
   mapping each constraint prefix to a TABLE name and assuming the table was
   the resource — and `tools/gate1_verify.py`'s own header already warned:
   *"THE RESOURCE IS NOT THE TABLE and that is the whole trap this map exists
   for."* The map is corrected and `NOT_GOVERNED_HERE` now carries the third
   state.
2. **`rf_invoices` is not under-capped, it is UNCAPPED.** The gate reads
   `if (action === 'write')`. `rf_invoices` writes through `issue`,
   `add_payment`, `reconcile_claim` and `gl_export`, so **the cap never fires
   at all** — and the same is true of `rt_routes`/`rt_stops` (`upsert`,
   `reorder`, `optimize`), `alf_payer_rules` (`route`) and every other declared
   verb. §3.1.
3. **`grants` had no storage.** F2's widening branch has been unreachable since
   b18 because the call site passed a literal `null` — not an oversight,
   there was nowhere to read it from. Every module-level arm for it was green
   the whole time.

## 3. ROUTED — FOUND, MEASURED, NOT CLOSED

### 3.1 → whoever owns the write-cap policy. The cap gate covers ONE verb

    api/sd-data.js:892   if (action === 'write') { ...the payload cap... }

**Measured, not inferred:** every resource whose writes use a declared verb
rather than `write` passes that gate untouched.
`api/_resources/sairnroofing.js:245` declares
`rf_invoices: ['issue', 'add_payment', 'reconcile_claim', 'gl_export']`, and
`rf_invoices` carries `rfinv_data_size <= 262144`. So a 10MB `issue` payload is
refused by Postgres with an opaque error, which is the exact failure the
`MAX_PAYLOAD_BYTES` comment records paying for on slabs.

**NOT FIXED, and the reason is risk rather than effort.** Extending the gate to
every write-class verb would start refusing payloads that work today — a
200-stop `rt_routes` upsert is the obvious one, and `optimize` carries the same
stop list. b29 was sent at closing known caps, not at changing what the gate
covers. **Next step:** enumerate `EXTRA_ACTIONS` into write-class and
compute-only, measure the largest real payload per write-class verb, then cap
per `(resource, action)` rather than per resource. Arm **C7b** of
`api/b28-photo-cap.test.js` keeps the declaration honest in the meantime.

### 3.2 → Michael. `sql/sairnlegacy_settings_livery_grants.sql`, one column

**Written, not run.** It adds `livery_grants jsonb not null default '{}'` to
`public.sairnlegacy_settings` — the storage F2's per-employee half has never
had. **Running it grants nobody anything**: the default is an empty map, and
two separate things must be true before one driver reads one booking (the home
sets `direct_to_family`, AND somebody with personnel authority writes that
employee's id into the map).

**The handler works before and after**, which is the point: a missing column
answers 400 undefined_column, `api/sd-data.js` re-issues the read without it,
and the answer is a REFUSAL. Arm **G5** of `api/b29-funeral-f2-f3.test.js` is
that case and it is the state production is in today.

### 3.6 `sd_locations` — the measurement, and what it could not tell

Michael's decision: 16,384 is the intended number; measure the largest real row
first. **Measured live on `SD-AUDIT-2026`: the table answers
`provisioned: false`, zero rows.** That is a could-not-tell about other
licences and is recorded as one.

**The decisive argument is not the sample, it is the constraint.**
`sdlocations_data_size check (octet_length(data::text) <= 16384)` means Postgres
has refused every row above 16,384 for as long as it has existed, so **no
stored row anywhere can be above it** and lowering the API cap to that number
cannot refuse a write that works today. Arm **C8** records the derivation.

## 4. THE PARALEGAL DECISION, AND WHY IT IS A SECOND SET

Michael's words: *"goes back on the IOLTA reconcile list as PREPARE-ONLY."*

**The literal reading — `paralegal: true` on `LAW_RECONCILE_ROLES` — would have
delivered the exact state b20 withdrew the grant to avoid:** a non-lawyer
producing a finished reconciliation that nothing records a lawyer as having
reviewed, on the one figure a bar association audits. So the grant went on a
**second** set, `LAW_RECONCILE_PREPARE_ROLES`, and the gate admits either.

**The half that makes it safe is the stamp, not the permission.** Every
reconcile reply now carries `attested: false`, `prepared_by_role`,
`prepare_only` and `attestation_required_from` — **including an owner's own
run**, because running the comparison and attesting to it are two acts even
when one person does both. `attested: recMayRun` would have been the
natural-looking one-liner and is the lie the stamp exists to prevent; arm **P4**
is that case.

**Still open and not mine:** `sql/sairnlaw_trust_attestations.sql` has not been
run, so `api/law-attest.js` answers 503 on every write and no attestation can
actually be recorded yet. The grant was made anyway because the reply is
stamped regardless, so an unprovisioned table cannot be mistaken for a recorded
attestation. `LAW_RECONCILE_ATTESTATION.gap` says exactly that and nothing more.

## 5. THREE DEFECTS I INTRODUCED AND THE CONTROLS CAUGHT

Recorded because the controls are the finding, not the slips.

1. **A LITERAL BACKSPACE in a regex.** `/detail: *(null|...)\b/` was authored
   through a script and `\b` reached the file as **byte 0x08** rather than a
   word boundary, so the null exclusion silently never fired. **C1 was green at
   the time** — the real source happens to contain no `detail: null` in a
   response. Only **C2**, which runs the same function over a fixture that
   SHOULD match, could tell. This platform has written this exact defect down
   once already: *"a regex that shipped with a literal backspace and could
   never match."*
2. **A fixed-width span.** The sweep took twelve lines after each
   `res.status(`, which from a one-line response ran into the next statement
   and flagged an internal `auditAlf({ ... detail: detail ... })`. **C2 caught
   that too**, on a fixture, before C1's zero could be believed.
3. **My own comment tripping my own scanner, twice.** `S2` of
   `api/b29-rt-stops-hash.test.js` asserts there is no `routeHash || licHash`
   fallback — and the fix's comment EXPLAINS why there is no such fallback,
   containing the string. Both sweeps now read comment-stripped source. The
   answer is to blank comments, never to stop writing the reason down.
