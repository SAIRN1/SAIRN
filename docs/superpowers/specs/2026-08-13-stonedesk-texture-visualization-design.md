# StoneDesk — Texture-Only Stone Visualization (Drawing Tool)

## Problem

Every shape the Drawing Tool renders — straight, L-shape, U-shape, galley, custom-drawn polygon — fills with one hardcoded placeholder color (`rgba(232,133,10,0.1)`, a faint orange tint), duplicated verbatim across ~5-6 separate call sites in `drawCTPreview()`, regardless of what material the rep actually selected. A client looking at their quoted countertop sees a flat translucent orange rectangle, not anything resembling granite, marble, quartzite, or quartz. Real value: render something that actually looks like the client's stone choice.

**Explicit legal boundary, load-bearing for this entire feature:** this renders a *representative* color/pattern for a stone *category* — never tied to, generated from, or suggestive of any specific photographed slab, quarry, or named stone product. No image assets, no photos, no slab-specific naming anywhere in code, comments, or UI copy. This is what keeps the feature clear of the existing patent family covering actual-slab-photo visualization (confirmed prior to this spec). Any future change that introduces real slab imagery, quarry-specific naming, or anything positioned as "this is what your actual slab looks like" is explicitly out of bounds for this feature and would need its own legal re-check, not a quiet extension of this one.

## Scope, decided during brainstorming

- **New dedicated appearance picker**, independent of the existing pricing-tier `#material` dropdown. That dropdown's 10 values (e.g. "Granite — premium / exotic") carry no color/pattern information — two reps picking the same pricing tier could mean very different-looking stone. A separate picker answers "what does it look like," not "what tier is it priced at."
- **Two simple axes:** Stone Type (Granite / Marble / Quartzite / Engineered Quartz — the same 4 families already used as `#material`'s optgroup labels) picks the *pattern* (each family's real typical character); Color Tone (Light / Medium / Dark) picks the *base color*. 4×3 = 12 combinations. Both default to unset — unset renders exactly today's flat placeholder, so this feature changes nothing for a rep who never touches the picker.
- **Procedural canvas drawing only.** No image assets, no `ctx.createPattern()` over bitmap swatches. A base fill color plus programmatically-drawn speckle dots or vein strokes, generated by canvas 2D drawing calls at render time. Adds no file-size weight to the single-HTML-file app, and is the cleanest possible distance from anything photographic.
- **Preset and Custom Draw modes only.** Room Layout (`dcMode==='room'`) is out of scope — same precedent as chamfered corners, raised bar, and canvas zoom before it, all of which excluded Room Layout's own independent renderer.
- **Persisted with the saved quote.** `stoneType`/`colorTone` are added to the saved-quote-drawing-state feature's existing capture/restore functions, so a reloaded quote's canvas looks the same as when it was saved — same pattern as every other job-detail field that feature already handles, not a new persistence mechanism.

## Architecture

Pure client-side addition to `stonedesk.html`. No new files, no build step, no server/API changes, no image assets.

**Data:** two new module-level state fields (alongside the existing `ctShape`/`dcPoly`/etc. globals), e.g. `var dcStoneType = null; var dcColorTone = null;` — `null` means "unset," which every rendering call site treats as "use today's flat placeholder."

**Picker UI:** a new small card in the Drawing Tool's left panel (same visual style as the existing job-detail cards — `draw-material`, `draw-edge`, etc.), with two button rows or dropdowns: Stone Type (4 options) and Color Tone (3 options), each `onchange`/`onclick` setting the corresponding global and calling `drawCTPreview()`, matching every existing field's wiring convention in this file.

**Rendering — the core consolidation:** one new function, `dcApplyStoneFill(ctx, x, y, w, h)` (rect form) plus a polygon-path variant for Custom Draw mode (or one function taking either a rect or a path callback — exact signature is an implementation-plan decision, not a spec-level one). Called at every one of the ~5-6 places `drawCTPreview()` currently does:
```js
ctx.fillStyle='rgba(232,133,10,0.1)'; ctx.beginPath(); ctx.rect(x,y,w,h); ctx.fill();
```
Internally:
1. If `dcStoneType`/`dcColorTone` are unset: fill exactly as today (`rgba(232,133,10,0.1)`) — zero visual change from the current baseline.
2. If set: look up a base color from a small `STONE_TONE_COLORS` table keyed by `stoneType+colorTone` (12 entries, hand-picked representative colors — e.g. Granite/Dark → a dark charcoal grey, Marble/Light → an off-white, etc.).
3. `ctx.save(); ctx.beginPath(); <rect or polygon path>; ctx.clip();` — clips all subsequent drawing to the exact shape being filled, so texture primitives never spill outside it regardless of whether the shape is a simple rect or an arbitrary Custom Draw polygon.
4. Fill the clipped region's bounding box with the base color.
5. Draw texture primitives within the bounding box, per stone type:
   - **Granite:** scattered small speckle dots in 2-3 tones derived from the base color.
   - **Marble:** a handful of soft curved vein strokes (bezier curves) in a lighter/darker tone than the base.
   - **Quartzite:** vein strokes like Marble's, but sparser and thinner — quartzite typically shows subtler veining than marble.
   - **Engineered Quartz:** very fine, sparse speckle — matches quartz's manufactured near-uniform look.
6. `ctx.restore();`.

**Stability across re-renders:** `drawCTPreview()` fires on nearly every input change (typing a dimension, dragging an edge). Texture primitive positions/curves are generated by a small seeded pseudo-random generator, seeded from a deterministic combination of the shape's own dimensions plus `stoneType`+`colorTone` (e.g. a simple string hash of `aL+'|'+aD+'|'+stoneType+'|'+colorTone` feeding a small PRNG like mulberry32). Identical inputs always regenerate an identical layout — no flicker while editing unrelated fields — but a real dimension change naturally produces a different layout, which is correct (the texture redraws to fit the new size), not a bug.

## Explicitly out of scope for this pass

- Room Layout mode's own independent renderer — untouched.
- Any image asset, bitmap pattern, or `ctx.createPattern()` over a raster image.
- Any reference to a specific quarry, slab, or named commercial stone product anywhere in code, UI copy, or comments.
- Deriving texture from the existing pricing-tier `#material` dropdown — that field remains pricing-only, untouched by this feature.
- The printed cut sheet (`printDrawCutSheet()`) — a text-only fabrication document with no canvas/visual rendering; nothing to add texture to there.
- Changing pricing, cost calculation, or any dollar figure — this is a purely visual feature.

## Edge cases

- **A shape too small to fit any texture primitive** (e.g. a tiny corner section): the base color fill still applies; texture primitives that would render off-canvas or overlapping-degenerate are simply skipped by the generator's own bounds checks — never an error, worst case is a shape that reads as a flat color at a size too small for texture to read anyway.
- **Switching stoneType/colorTone mid-session:** each change re-seeds and redraws — no stale texture from a previous selection can persist, since the seed itself includes both fields.
- **A saved quote from before this feature shipped** (no `stoneType`/`colorTone` in its `drawingState`): both restore as `null`/unset, rendering the same flat placeholder that quote always rendered — no visual change to old quotes, no error.
- **Custom Draw mode's polygon clip:** since `ctx.clip()` accepts any path, the same `dcApplyStoneFill()` logic that works for Preset mode's simple rects works unmodified for Custom Draw's arbitrary polygon — no separate texture-drawing implementation needed for that mode.

## Testing / verification plan

Same cycle as every drawing-tool feature shipped this session: `node --check` via `tools/checkblocks.py` on every touched block, scoped Guardian mechanical checks, per-task review during implementation, commit, push, then live-verify against `sairn.vercel.app/stonedesk`. Specifically: confirm an unset picker renders byte-identical to today's baseline (no regression); confirm each of the 12 stoneType/colorTone combinations renders a visually distinct base color and pattern style on both a Preset rect and a Custom Draw polygon; confirm re-rendering the same shape with the same selection twice in a row (e.g. two consecutive `drawCTPreview()` calls with no input change) produces pixel-identical output (the seeded-stability requirement); confirm changing a dimension after selecting a texture produces a different-but-still-textured layout, not a reversion to the flat placeholder; confirm save→reload round-trips the selection through `dcSnapshotDrawingState()`/`dcLoadDrawingState()` the same way Task 4 of the prior feature verified every other job-detail field.
