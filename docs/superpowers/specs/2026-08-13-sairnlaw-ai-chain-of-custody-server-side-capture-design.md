# SAIRNlaw AI Chain of Custody — Server-Side Capture (Gap 1 fix)

## Problem

Phase 1 (shipped this session, `origin/main` at `c4980ce`, migration live-verified end-to-end) logs AI interactions via a second, unlinked, fire-and-forget client request AFTER the AI response already rendered in the chat. `SAIRN-BACKLOG.md` disclosed the real consequence: capture isn't guaranteed (a closed tab, a blocked second request, or simply not calling the log endpoint produces a real AI interaction with no record) and isn't tamper-evident against fabrication (nothing ties a logged prompt/response pair to a real Claude call — a client could submit an invented pair). Real goal: a response literally cannot reach the rep without a genuine log entry already existing.

**Verified starting state (2026-08-13):**
- `sendAI()` is not the only real AI call site. Grep of `sairnlaw.html` for `PROXY` (`https://sairn.vercel.app/api/claude`) found **5 call sites across 4 functions**: `sendAI()` (two legs — the tool-use turn and its follow-up), `explainReconciliation()` (trust-accounting explanations, no matter link), `runAiDraft()` (matter-linked document drafting — already has a real `matterId`), `reviewDocument(docId)` (AI review of an actual uploaded matter document, whose record already carries a real `matter_id`). Only `sendAI()`'s two legs were brought into Chain of Custody in Phase 1 — the other 3 were never logged at all, not just logged-unreliably.
- `api/claude.js` (the endpoint all 5 currently call) is a thin, fully generic proxy shared by 17 SAIRN apps (`KNOWN_APP_IDS`) — no session-token concept, no per-app logic, `app_id` + `is_demo` rate-limiting only. Confirmed by reading the full file (170 lines).
- `runAiDraft()` already saves its successful output as a real `law_matterdocs` record (`doc_type:'AI Draft'`) — unrelated to Chain of Custody, pre-existing behavior, must not be disturbed by this change.
- `sendAI()`'s tool-use flow has a real client-side data dependency: `lawExecuteTool()` reads local `law_*` resources (matters, deadlines, etc.), which are not server-accessible (same platform-wide gap already tracked in `SAIRN-BACKLOG.md` for `law_trusttx` and 17 other resources). The server cannot execute this step itself without that prerequisite — out of scope here.

## Scope, decided during brainstorming

- **All 5 call sites, all 4 functions** — not just `sendAI()`'s two. Leaving the other 3 unlogged would mean the feature's own "every AI interaction is logged" claim stays false for the call sites most likely to produce real filing content (`runAiDraft()` especially).
- **New logic lives as one more action (`ai_generate`) in the existing `api/law-auth.js`**, not a new file — reuses its already-hardened session verification, `audit()` writer, and error conventions with zero new boilerplate. `api/claude.js` itself is not modified behaviorally for its other 17 callers; its actual Anthropic-calling logic is extracted into a small reusable function both files import, so ~30 lines of demo-limit/API-key/error-handling logic isn't duplicated.
- **Write failure blocks the response.** If the audit-log write fails after Claude has already generated real text, the endpoint returns an error instead of the text — the rep never sees an AI answer that wasn't logged. This is the literal mechanism that closes the capture gap, not just documentation of intent.
- **The logged prompt is the full, real text sent to Claude** — matter facts, document text, reconciliation numbers included, not a paraphrase of the rep's short request. More complete and defensible; storage cost already handled by Phase 1's existing 20,000-char insert cap and 500-char list-preview truncation.
- **The standalone `ai_log` action (Phase 1) is removed**, not left in place unused. Once `ai_generate` writes every log entry itself from a real Claude response, a still-open action accepting an arbitrary client-supplied prompt/response pair is a residual fabrication backdoor, not a redundant safety net — removing it is what actually closes the fabrication risk this fix exists for.

## Architecture

**`api/claude.js` refactor (minimal, behavior-preserving for its other 17 callers):** extract the Anthropic-calling block (API key check, the `fetch('https://api.anthropic.com/v1/messages', ...)` call, response/error shaping) into an exported function, e.g. `callAnthropic({system, messages, max_tokens, tools})` returning `{ok, status, data}` (or throwing on a real network failure, matching this file's existing `try/catch` shape). The existing `claudeProxyHandler(req, res)` — used by every other app via HTTP — becomes a thin wrapper: validate `app_id`/`is_demo`/rate-limit exactly as today, then call the new function and write its result to `res` exactly as today. `module.exports` gains the new function alongside the existing handler (matching this file's existing pattern of exporting `sanitizeTools` alongside the handler). No change to the HTTP contract, rate limiting, demo-key logic, or `KNOWN_APP_IDS` gate — every one of the other 17 apps calls the exact same endpoint, unaffected.

**`api/law-auth.js`: new `action: 'ai_generate'`.** Request body: `{system, messages, max_tokens, tools (optional), matter_id}`. Flow:
1. `verifySessionToken(tokenFromRequest(req), licHash, APP)` — any authenticated role (generation itself isn't review-gated; only review/reject/filing-attestation are `owner`/`attorney`-only, unchanged from Phase 1).
2. Call the extracted `callAnthropic({system, messages, max_tokens, tools})` (a direct in-process function call, not a second HTTP round-trip).
3. If the response contains a `tool_use` block and no final text: return it to the client as-is, **unlogged** — nothing user-facing has been served yet, so there is nothing to log. The client executes the tool locally (unchanged) and calls `ai_generate` again with the tool result appended to `messages` for the second leg.
4. If the response contains final text (the only case a rep ever sees output): write the audit-log entry — `prompt` = the real, full `messages` content actually sent (JSON-stringified or the last user-turn content, whichever the plan settles on precisely), `response` = the real text received, `matter_id` from the request, `tools_used` = any tool name(s) actually invoked this exchange — **before** responding to the client. If the write fails, respond with a real error (matching `LOG_WRITE_FAILED`'s existing shape from Phase 1); do not include the AI text in that response under any circumstance.
5. Only on a successful write: return the real Claude response to the client.

**Client (`sairnlaw.html`):** all 5 call sites switch from `fetch(PROXY, ...)` to a session-authenticated call to `ai_generate` (via `lawAuth('ai_generate', {...}, true)` or an equivalent thin wrapper). `lawLogAiInteraction()` (Phase 1's fire-and-forget client-side logger) and its two call sites inside `sendAI()` are removed entirely — logging is no longer a second, client-initiated request. The existing required matter picker on `sendAI()`'s panel is unchanged; `runAiDraft()`/`reviewDocument()` pass their own already-known real `matter_id`; `explainReconciliation()` passes `'general'`.

**`ai_log` removed.** Deleted from `ACTIONS` and its handler removed from `api/law-auth.js`. No other code calls it after this change lands (confirmed by this plan's own migration of all 5 real call sites away from the old pattern in the same pass).

## Explicitly out of scope for this pass

- Making `sendAI()`'s tool-use FIRST leg (the one that only produces a `tool_use` directive) itself require a matter link or get logged — it produces no user-visible content, so there's nothing to attribute yet; only the leg that returns final text is in scope for logging.
- Server-side tool execution / making `law_matters` (or any other `law_*` resource) server-backed — a real, much larger, separately-tracked platform-wide gap (already in `SAIRN-BACKLOG.md`), a hard prerequisite for that specific change, not something this fix can or should absorb.
- Gap 2 (unvalidated matter linkage) — explicitly a separate, already-disclosed gap in `SAIRN-BACKLOG.md`, blocked on the same `law_matters` server-backing prerequisite above. `runAiDraft()`/`reviewDocument()` passing their own real (but still client-side, still unvalidated) `matter_id` is a genuine improvement in THIS pass — more reliable than a manually re-picked dropdown — but does not close Gap 2, which requires server-side validation against a real matters table that doesn't exist yet.
- Any change to Phase 1's review workflow (`ai_review`/`ai_reject`/`ai_used_in_filing`) — those already operate on whatever rows exist in `sairnlaw_audit_log` regardless of how they were written; this fix changes only how rows get created, not how they're reviewed.
- Any change to the 3 accepted-and-documented nits already in `SAIRN-BACKLOG.md` (ai_list volume-scoping, native `prompt()` for reject reasons, no `ai_log` volume cap — the last of which becomes moot once `ai_log` itself is removed).

## Edge cases

- **A tool-use exchange whose second leg's log write fails:** the rep sees a real error on the SECOND request (the one carrying final text) — the first leg's tool-use directive was never logged and never needed to be; no partial/orphaned log entry results from a failed second leg, since nothing was written until that point.
- **`explainReconciliation()`/`reviewDocument()` calling `ai_generate` with no tools at all:** the branch-on-`tool_use` logic in step 3/4 above degrades correctly — Claude never returns a `tool_use` block when no `tools` were sent, so every response from these three functions always hits the "final text" logging path on the first and only call.
- **A rep with a valid session but a since-deleted/renamed matter** (`runAiDraft()`/`reviewDocument()`): the client still sends whatever `matter_id` it has locally — same disclosed Gap 2 limitation as today, not worsened or improved by this fix beyond what's already logged in the backlog.
- **`callAnthropic()`'s own failure** (Anthropic API error, network failure): surfaces as a real error from `ai_generate` before any logging is attempted — no log entry is written for a request that never produced a real response, matching the existing `LOG_WRITE_FAILED` pattern's spirit (never log something that didn't really happen).

## Testing / verification plan

Real, DB-backed, using the already-provisioned `LAW-TEST-2026` test license (not simulated): call `ai_generate` for each of the 4 functions' real request shapes (with and without tools) and confirm a real row lands in `sairnlaw_audit_log` with the real prompt/response/matter_id/tools_used, confirm the response is withheld (a real error, not the AI text) when the log write is made to fail (e.g. a temporarily-invalid `event_type`, reverted after the check), confirm `runAiDraft()`'s existing `law_matterdocs` "AI Draft" save behavior is unaffected, confirm the tool-use first leg genuinely produces no log row, confirm `ai_log` is genuinely gone (a direct call to that action now 400s as an unrecognized action), and confirm all 17 other apps' `api/claude.js` calls are still byte-identical in behavior (spot-check one, e.g. StoneDesk's own AI panel, live).
