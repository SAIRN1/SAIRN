## ITEM 1 — THE REVOKE WINDOW IN `api/agent/register.js`

> **CONCEPT.** A registration must not RESURRECT a revoked agent: the
> not-revoked condition travels **in the same statement** as the update, and a
> zero-row result is a **REFUSAL**, never a success.

**The window, exactly as the dispatch described it.** The handler read
`status`, refused if `'revoked'`, and then wrote `status: 'active'` with an
**id-only** filter and `Prefer: return=minimal`. Anything that revoked the agent
between the read and the write — a support action, the Stripe webhook, a second
concurrent register — was **silently overwritten**, and the caller got
`ok: true`.

**The fix is two halves and the suite proves BOTH are needed.**

1. `&status=neq.revoked` on the PATCH — a compare-and-set, the same shape
   `api/_lib/countersign.js` uses for `&spent_at=is.null`.
2. `Prefer: return=representation` plus a zero-row check. **With `minimal`,
   PostgREST answers 204 whether it changed one row or none**, so the condition
   would be enforced in the database and invisible to the handler — *a guard
   nothing can read is a guard that reports success on a refusal.* Ablation
   **D2** removes only this half, leaves the URL condition in place, and arm A1
   still goes red.

A zero row count and a **non-array body** both refuse with the **same 403 and
the same message** as the pre-write check: a caller must not be able to tell the
race from the ordinary refusal and try to win it.

**Reproduced with a recorded PostgREST that revokes the row the instant the read
returns** — the real window, which cannot be reproduced by stubbing one answer —
and with **two concurrent calls** (arm A8), which both succeed on a live agent,
because the new condition is `neq.revoked` and not a single-use lock.

## ITEM 2 — THE ZERO-ROW PATCH IN `api/agent/stripe-webhook.js`

> **CONCEPT.** The log line must say what the **write did**, not what was
> **asked for** — so a PATCH that matched no row is reported as having changed
> nothing, and never as a plan_status that was set.

`setPlanStatus()` used `Prefer: return=minimal`, so `res.ok` was true for one row
updated **and for none**, and then logged:

    Agent <id> plan_status set to "paid" via Stripe webhook.

**That line is the only record this endpoint leaves.** Stripe gets its 200 and
never retries, nothing reconciles the two sides, and during a billing dispute the
one artefact an operator reads says the opposite of what happened. A paid
customer whose agent row was never updated looked, in the log, exactly like one
whose was.

**Three outcomes now, on two streams:** a real change → `console.log` **with the
row count**; no row matched → `console.error` naming the id and saying
plan_status was **NOT** set; could-not-read-the-count → `console.error` as
**UNCONFIRMED**.

**It does not throw**, and that is a decision. Throwing would make Stripe retry
an event that can never succeed, forever. The distinction needed is between
*did it* and *did nothing*, and both are normal outcomes for a webhook whose
payload names a row this database may not have.

## ITEM 3 — TWO CONTROLS THAT DEFAULTED PERMISSIVE

> **CONCEPT.** A control whose setting is **missing or misspelled** must refuse,
> not permit. `observe` and `enforce` are the only two answers either flag has,
> and anything else — absent, empty, whitespace, a typo — is a configuration
> nobody made, and is treated as `enforce`.

Both reads were one line, both obviously correct in isolation, and both had the
**same two holes**:

    api/claude.js             String(process.env.SAIRN_CLAUDE_AUTH_MODE || 'observe')
    api/_lib/ai-rate-limit.js String(process.env.SAIRN_AI_RATE_LIMIT_MODE || '')
                                .toLowerCase() === 'enforce'

An **absent** variable permits, and so does a **misspelled** one, because every
spelling that is not exactly `enforce` falls into the same branch as `observe`.
`api/_lib/fail-closed-mode.js` now carries the rule and **both** call it, so the
two cannot drift into disagreeing about what an unset flag means.

**The third answer is the point:** `{ mode: 'enforce', configured: false,
reason }`. A control that silently **hardened** is as hard to operate as one that
silently relaxed, so the reason names the variable and quotes what it actually
held, and `api/claude.js` logs it once per request when it was not configured.

**THE DEGRADED AXIS IS DELIBERATELY UNTOUCHED.** *"I could not reach the
counter"* still fails open in the rate limiter: that is a **measurement** failure,
not a configuration one, and enforcing a limit nobody could count is the worst of
both worlds that file's own header warns about.

**One arm was RE-AIMED rather than deleted.**
`api/_lib/ai-rate-limit-tenant.test.js` asserted `allowed === true` with the
comment *"observe mode must still allow"* — while its own harness **deletes**
`SAIRN_AI_RATE_LIMIT_MODE`. What it was really asserting is that an **unset flag
permits**. The arm exists for `limited_by`; the `allowed` expectation is now set
**explicitly on both sides** so it says which mode it is testing instead of
inheriting one from a deleted variable.

### WHAT THE DEPLOYED ENDPOINT ACTUALLY DOES TODAY — MEASURED

Driven against `https://sairn.vercel.app/api/claude` **before** this change
deploys:

| probe | answer | reading |
|---|---|---|
| unauthenticated POST, valid `app_id` and `messages` | **401 `NO_LICENSE`** | **`SAIRN_CLAUDE_AUTH_MODE` IS set to `enforce` in production.** The fail-closed change is a **no-op on the deployed auth path** |
| same call with `SD-AUDIT-2026` | **200**, a real completion from `claude-sonnet-4-6` | the licence gate is the only thing refusing |
| **a burst of 12 authenticated demo calls** | **12 × 200, zero 429, zero `rate_limit_degraded` flags** | **this does NOT show the limiter is in observe** |

**THE SECOND READING IS THE HONEST ONE AND IT IS THE FINDING.** Twelve calls in
a row being allowed is consistent with `observe`, and equally consistent with
`enforce` under a daily ceiling far above twelve. **The response carries no mode,
so from outside the deployed rate-limit mode is NOT OBSERVABLE AT ALL** — only
the auth half is. That is precisely the gap the dispatch named, and probing did
not close it; it measured that it cannot be closed from here.

**SO THERE IS A REAL DEPLOY-TIME RISK AND IT IS THE TOP OPEN ITEM.** If
`SAIRN_AI_RATE_LIMIT_MODE` is **absent or misspelled** in Vercel, this change
switches the cost limiter **ON** at the daily ceiling the moment it deploys.
`vercel env ls production --project sairn` prints the names (not the values) and
is the check. Named loudly rather than softened, because the change is the one
that was asked for.
