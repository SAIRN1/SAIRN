## 1. The permission rules: two parts of the brief are NOT expressible, and one documented behaviour did not hold

The rules are in `.claude/settings.json` (committed, so every clone takes them
by rebase) and in `~/.claude/settings.json` (edited directly, with
`settings.json.bak-b5` beside it). **deny 75 / ask 0 / allow 79** in the
project file; **deny 85 / ask 0 / allow 91** at user level, where the 25
pre-existing deny rules were **merged, not replaced** — a rule somebody added
on purpose is not this session's to drop.

Both `ask` lists are now **empty**. That is the point: every entry that was in
them (`git add`, `git commit`, `git push`, `npx vercel`, `rm -rf *`,
`git reset --hard *`, `git clean *`, `git branch -D *`) is now either an ALLOW
or a DENY, so none of them produces a prompt.

### The matcher facts the rules are built on

Verified against the current Claude Code permission documentation before a
single rule was written, not assumed:

| Fact | Consequence for these rules |
|---|---|
| `Bash(rm *)` and `Bash(rm:*)` are identical; `:*` is only recognised at the end | one form used throughout, never mixed |
| the space before a trailing `*` is load-bearing — `Bash(ls *)` does not match `lsof`, `Bash(ls*)` does | delete rules carry both spellings |
| **deny always wins**, at every level, and an allow can never carve an exception out of a deny | this is what makes `Bash(git push *)` safe to allow while every force spelling is denied |
| a compound command is split and each subcommand matched independently, including inside `$( )` | a deny fires on `cd /tmp && rm -rf x` |
| deny rules match past a leading env assignment; **allow rules are documented not to** | see the failure below |
| Read/Edit deny covers Bash redirects and `cat`/`sed`/`tee`, but **not** a subprocess that opens the file itself | the python hole below |

### What was measured

| class | command driven | expected | observed |
|---|---|---|---|
| delete | `rm --help` | DENY | **DENIED** |
| force, against the broad allow | `git push --force --dry-run origin main` | DENY | **DENIED** |
| force, as the 2nd element of a compound | `echo start && git reset --hard HEAD --quiet` | DENY | **DENIED, whole compound** |
| force, inside a subshell | `echo "x: $(git clean -f --dry-run)"` | DENY | **DENIED, whole command** |
| network | `curl --version` | DENY | **DENIED** |
| installs | `npm install --dry-run --help`, `pip install --help` | DENY | **DENIED** |
| discard, exact rule | `git checkout . --help` | DENY | **RAN** — see below |
| discard, after widening | `git checkout HEAD . --dry-run` | DENY | **DENIED** |
| settings edit | Edit tool on `.claude/settings.json` | DENY | **DENIED** — *"File is in a directory that is denied by your permission settings."* |
| `SAIRN_SEED_GATE=off` | `SAIRN_SEED_GATE=off git push origin main --dry-run` | PROMPT | **RAN, no prompt** — see below |
| allow | `git status`, `grep`, `python -c`, every Edit this batch | ALLOW | ran |

**The rules took effect immediately — no restart was needed for this session's
own tool calls.** That is measured, not assumed: `rm --help` was denied on the
first attempt after the file was written.

### Finding A — an exact deny rule is exactly exact, and the first draft had a hole

`Bash(git checkout .)` has no trailing `*`, so it matched only that exact
string. `git checkout . --help` ran. Harmless in itself, and the proof that
mattered: **`git checkout HEAD .` discards the entire working tree and matched
nothing in the first draft**, because the broad `Bash(git checkout *)` was in
the ALLOW list underneath it.

Fixed two ways, because one was not enough: every discard spelling gained a
wildcard form in deny (`git checkout . *`, `git checkout HEAD .`,
`git checkout HEAD -- . *`, the `git restore` equivalents), **and the broad
`Bash(git checkout *)` allow was removed.** Chasing spellings in the deny list
while the broad form sits in allow is the losing half of that race. A branch
switch now prompts, which is the right side to err on.

### Finding B — `SAIRN_SEED_GATE=off` cannot be stopped by permission rules at all

**DECISION NEEDED — this is the one the brief asked for and it cannot be
delivered as a rule.**

- As a **deny**: not expressible. Deny rules match *past* a leading env
  assignment, so the assignment is stripped before matching and the rule text
  never sees it.
- As a **fall-out-of-allow**: documented to work, and **it did not**.
  `SAIRN_SEED_GATE=off git push origin main --dry-run` **ran with no prompt**.
  The allow rule `Bash(git push *)` matched past the unknown assignment. The
  local settings file was checked and carries no `git push` allow, so the match
  came from the new project rule.

So the blanket override remains reachable and silent. The only real control is
the gate-side design in **§4 below** (queue item 7), which is why that item
matters more than it looked.

### Finding C — the python hole, stated rather than hidden

`Bash(python *)` and `Bash(node *)` are allowed broadly, because every tool,
probe and gate in this repo runs through them, and narrowing to
`python tools/*` would put a prompt on every heredoc this platform runs on.

A deny rule **does not reach a subprocess that opens files itself**. So an
allowed `python -c` can do what the shell is denied — including rewriting
`.claude/settings.json`, which is how the user-level file was edited this
batch. **Measured, not theorised.** This is the trade implied by "stop
prompting me"; it is recorded here so nobody later reads the deny list as a
security boundary. It is not one. It stops accident and habit.

### Finding D — "network fetches except GitHub/Supabase/Vercel" is not one rule

An allow cannot except a deny. So the shell fetchers (`curl`, `wget`,
`Invoke-WebRequest`, `Invoke-RestMethod`, `nc`) are **denied outright**, and
the exception is served two ways that *are* expressible and are allowed:

- `tools/sairn_http.py` for scripts — which is already the house rule, since
  PR §3.2 forbids bare `curl` for live verification;
- `WebFetch(domain:...)` allows for `github.com`,
  `raw.githubusercontent.com`, `api.github.com`,
  `objects.githubusercontent.com`, `supabase.co`, `supabase.com`,
  `vercel.app`, `vercel.com`, `sairn.vercel.app`.

**Cost, named:** `tools/fetch_blocked_doc.sh` shells out to `curl` and will now
be denied if an agent runs it. `tools/run_tlc.py` only *prints* a curl line for
a human, so it is unaffected.

### Finding E — the per-clone `settings.local.json` files are the real prompting story

`Documents\SAIRN-cc\.claude\settings.local.json` is **87,551 bytes with 1,325
allow entries and zero deny entries** — years of "don't ask again" approvals,
untracked, per-clone, and at *higher* precedence than the committed project
file. Every clone has one.

They cannot weaken the new rules (deny wins at every level, so e.g. their
`Bash(rm -f sql/__prepushprobe.sql)` entry is now dead), but they are why the
prompting pattern differs between clones, and they are not version-controlled.
**Not touched this batch** — they are each clone's own file.

### The restart step, per agent

The rules took effect **immediately** in this session without a restart, so the
honest instruction is the cheap one first:

1. **Nothing, if the agent is mid-session.** The project file is read from disk;
   a fetch/rebase that brings the new `.claude/settings.json` in is enough.
2. **`git fetch origin && git rebase origin/main`** in that clone, so the
   committed rules arrive. This is the only required step.
3. **If a prompt appears for something in the allow list**, that clone's
   `settings.local.json` is not the problem (allow is additive) — restart that
   session so the file is re-read: exit and relaunch `claude` in the clone.

**I verified step 1 only, in this clone.** Steps 2–3 are the mechanism and have
not been driven in another clone, because entering another clone's working tree
is not this session's to do.

> **Rule E — a document that states a tense or a number is only true as of the
> read behind it, and a long run must therefore restate it at the end.**
>
> Three artefacts in one batch recorded a figure that was overtaken before the
> batch closed: a report and a digest said `HEAD at close 2697518e` and were
> landed by a push that then needed four more commits; a handoff said five
> rebases and there were six. None was wrong when written.
>
> The rule is not "check your numbers". It is **structural**: any figure a
> document states about its own run — a HEAD, a count of commits, a pass/fail
> tally, a number of rebases — must be re-derived at the moment the document is
> finalised, and where it changed, the correction stays visible in the document
> rather than being quietly overwritten. A silently-updated number loses the
> fact that the first answer was reasonable, which is the only thing that tells
> a reader whether to trust the second.
