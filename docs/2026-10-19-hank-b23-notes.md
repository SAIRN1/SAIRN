## ITEM 3 — THE IOLTA RECONCILIATION ATTESTATION. THE ONE-LINE CONCEPT, STATED BEFORE ANY CODE

> **A completed three-way reconciliation becomes an ATTESTED record only when a
> bar-admitted person signs a hash of the exact comparison that was run; a firm
> that has EXACTLY ONE active owner/attorney may switch on a per-firm
> single-signer setting and attest alone, and every attestation taken that way
> is stored as `signer_mode: 'single'` on the row — so the record never claims
> two people looked when one did.**

That sentence is Michael's answer to **§6 of
`docs/2026-10-19-hank-b21-attestation-design.md`**, which named three
non-equivalent answers and could not choose between them. The answer taken is a
**hybrid of (2) and (3)**: the per-firm setting of (2), with the honesty of (3)
carried on the row rather than left implicit. Neither half works without the
other —

* **(2) alone** is the thing SAIRNlaw's own countersign schema already refused
  once: *a legal requirement is not something a licensee turns off in
  Settings*. A bare boolean would let any firm weaken the control.
* **(3) alone** records the truth but gives a solo attorney no route at all,
  which is §6's stated blocker.

So the setting is **not a preference**: it is a statement about the firm's
staffing, and it is **only accepted while that statement is true** — exactly one
active owner/attorney. Two enforcement points, and the second is the one that
matters:

1. **At SET time** — a firm with two bar-admitted employees cannot turn it on.
2. **At ATTEST time** — the count is re-derived from the employee table on every
   single-signer attestation. A firm that turns the setting on as a solo and
   later hires a second attorney does **not** keep the single-signer route: the
   stale setting authorises nothing. A check that only runs at set time is an
   authorisation that outlives its own precondition.

And the count **fails CLOSED**. If the employee table cannot be read the answer
is *could not tell*, which refuses — never "one, so go ahead". PR §1.11 on a
record a bar auditor reads.

### WHAT IS DELIBERATELY NOT WEAKENED

`api/_lib/countersign.js` says in its own header that it has **no
`require_two_person` policy table, no `set_policy` action, and NO
SELF-SIGNATURE, EVER**. None of those three narrowings is touched. The
single-signer attestation **does not go through the countersignature token at
all** — it is a separate, named path on a separate route, and the shared lock
keeps refusing a self-signature exactly as it did. A solo attestation is a
different KIND of record, not the same record with a check switched off.

### WHY A SECOND PROFILE AND A SECOND ROUTE RATHER THAN A WIDER ONE

The design note (§5) expected `law_trust_attestation` to be added to
`api/law-countersign.js`'s `lockedResources`, and predicted that arm **E3** of
`api/b18-countersign-lock.test.js` would go red and need re-aiming. **It is
built the other way, and that is a decision, not a shortcut:**

* `api/law-countersign.js` carries ONE `preparerRoles` for every resource it
  locks — `LAW_TRUST_PREPARE_ROLES`, which is `{ paralegal }`. Adding the
  attestation to that profile would mean **only a paralegal could prepare an
  attestation and an attorney could not**, which is wrong for a solo firm and
  wrong for any firm where the attorney runs the reconciliation themselves.
  Widening that list to fix it would change **C2's decided answer** for
  `law_trusttx` as a side effect — an orthogonal change to a policy Michael
  decided.
* So the attestation gets its own route, `api/law-attest.js`, with its own
  profile: `preparerRoles` `{ owner, attorney, paralegal }`, `signerRoles`
  `LAW_BAR_ADMITTED_ROLES`, `MODE_ALWAYS`.
* **E3 therefore stays GREEN and was not touched.** `law-countersign.js`'s
  locked list still equals `LAW_TRUST_TWO_STAGE`, because that is still true.

### WHY IT REUSES `sairnlaw_countersign_tokens`

Measured, not assumed: that table's `resource` column is `text not null` with
**no CHECK on its value** (`sql/sairnlaw_countersign_schema.sql:56`), and
Michael has already run that schema. So the two-signer path needs **no new
token table and no new SQL to work** — only the attestation RECORD table is
new. A second token table would have been a second copy of a lifecycle that is
already proven by 59 arms.

## ITEM 1 — THE DEPLOYED `/api/bridge` ABSENT-`?action=` REFUSAL. **LIVE-PROVEN.**

b22 pushed the fix, probed it, got **401**, and recorded it as UNVERIFIED
without retrying. Re-probed at 2026-10-19 against
`https://sairn.vercel.app/api/bridge`, POST, `tools/sairn_http.py`:

| probe | HTTP | `error.code` | reading |
|---|---|---|---|
| **no `?action=` at all** | **400** | `UNKNOWN_ACTION` | **THE ONE UNDER TEST. b22's fix is live.** |
| `?action=` (empty value) | **400** | `UNKNOWN_ACTION` | the falsy test covers the empty param, not just the absent one |
| `?action=maps-optimize` | 400 | `UNKNOWN_ACTION` | b21's half, still live |
| `?action=push` | 401 | `NO_LICENCE` | correct — a known action reaches `handlePush` |
| no `?action=` + `data_type:'proxy_get'` | 400 | **no code — `payload.url is required for proxy_get`** | **the legitimate caller is UNAFFECTED: it reached the proxy_get handler** |
| `?action=proxy_get` | 400 | same proxy_get message | same |

**THE SIXTH ROW IS THE ONE THAT MATTERS AND IT IS NOT THE ONE UNDER TEST.** Two
400s that mean opposite things: `UNKNOWN_ACTION` is the refusal, and
*"payload.url is required for proxy_get"* is the proxy_get handler asking for a
field. A probe that only read the status code would have reported the
body-signalled caller as refused. **The branch order — proxy_get matched ABOVE
the refusal — is load-bearing and is now live-proven, not just asserted.**

The absent-action message differs from the unknown-action one in words as well
as code (*"No action was given"* vs *"No such action: …"*), which is how the
two were told apart without trusting the status.

## ITEM 4 — THE RAW-POSTGREST-FILTER ARM, SABOTAGE-TESTED. **THE ARM CATCHES IT.**

Not in the live clone: `api/` was copied to the scratchpad (491 files), the
sabotage applied there, and the copy deleted afterwards. The live clone's
`git status` was checked before and after and shows only this batch's own
files.

1. **Baseline in the scratch copy: 9 passed, 0 failed.** An ablation measured
   against an unmeasured baseline proves nothing.
2. **One raw splice reintroduced** — `api/agent/result.js`, the `command_id`
   that b22's finding #1599 named, `encodeURIComponent(command_id)` →
   `command_id`. The patcher **refused on a non-unique anchor** and the anchor
   had to be widened to include `&agent_id=eq.`, because `command_id` is
   spliced at **two** sites in that file.
3. **Result: `5 passed, 4 failed`, and D1's message names it exactly:**

       FAIL D1. ZERO production files splice a value into a PostgREST filter...
            raw PostgREST filter interpolation found in 1 place(s):
            agent/result.js:66  command_id

   **A1, C1 and C2 went red too, and that is the arms working rather than
   noise.** A1 drives the real handler and sees the `&` count change; C1/C2 are
   ablation arms whose anchors reference the *encoded* text, so they reported

   arm"* — the staleness message doing its job.
4. **Restored**, and the live clone re-run: **9 passed, 0 failed.**

**THE RULE IS NOW STANDING,** per Michael: *a value concatenated into a
PostgREST filter must pass through `encodeURIComponent` (or the file's
namespaced encoder) **at the point of concatenation***. Recorded in hank's
persistent memory as `postgrest-filter-encoding-is-a-standing-rule` so it
