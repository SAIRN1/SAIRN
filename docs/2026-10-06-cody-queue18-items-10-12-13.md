## ITEM 13 — THE 2x-BOUND RULE, AND THE FIVE TOOLS OF MINE IT APPLIES TO

### The rule

> **ANY `COULD NOT RUN` OR TIMEOUT-LIMITED VERDICT IS RE-RUN ONCE AT 2x THE
> BOUND BEFORE IT IS REPORTED.** A bound is a property of the harness, not of
> the subject, so a verdict produced by one is a statement about the harness
> until it has been re-asked. The re-run is cheap; publishing a floor as a
> verdict is not.

**What it cost to learn.** `CORPUS_TIMEOUT` was 45s and
`cross_tenant_isolation_scope.py` needs 131s, so 21 of its rules reported *"no
fixture lock and no control to ablate against"* — false about the half that
mattered. Re-asked at 200s: **21 of 21 answerable, and FOUR ARE DEAD.** The
bound was not mislabelling those rules as unknown; **it was hiding four
findings**, for as long as the tier had existed.

**And the rule has a second clause, learned the same day:** if the 2x re-run
also does not finish, **no bound is set at all.** `run_all_tests.py` and
`guard_ablation.py` were each given 420s and neither finished. **A bound from a
measurement that did not complete is an invented number.**

### Applied to every tool of mine with a fixed timeout

Derived from `docs/tool-owner-map.json` (31 tools resolve to cody) intersected
with a scan for `timeout=` / `TIMEOUT=` on non-comment lines.

| tool | fixed bound(s) | rule applied |
|---|---|---|
| `tools/dead_rule_sweep.py` | 2, **45**, 240 | **DONE.** 45 is `CORPUS_TIMEOUT` — now overridable (`--corpus-timeout`), PRINTED on every run, with measured per-tool bounds in `TOOL_BOUNDS` at 2x headroom and an `UNBOUNDABLE` set for the two that cannot be timed. 2 is the deliberate quick re-ask that tells a timeout from a crash; 240 is the sandbox evidence bound |
| `tools/metamorphic_check.py` | **120** | **NOT DONE.** A 120s bound on the rewording family, no override and no printed bound. Applying the rule here is the next action on this tool |
| `tools/nhi_register.py` | 5, 20 | **NOT DONE.** Two short bounds on sibling-clone enumeration. Lower risk — a 5s git call that times out is itself a signal — but neither is overridable and neither prints |
| `tools/overrun_inversion_scan.py` | **120** | **NOT DONE.** Same shape as `metamorphic_check.py` |
| `tools/wait_for.py` | 4, **3600** | **NOT APPLICABLE, and it is the counter-example worth keeping.** This tool IS a bound — waiting is its whole job. A 2x re-run of a deliberate wait is not a correction, it is twice the wait |

**ONE OF FIVE DONE, THREE OWED, ONE EXEMPT** — and `wait_for.py` is why the
rule needs its exemption written in, rather than being applied mechanically to
every `timeout=` in the repo.

## INCIDENT, MID-BATCH — **THE CLONE WAS FLIPPED TO `core.bare = true` AND EVERY GIT WRITE FAILED**

Not an item. It happened while committing items 10–13 and it stopped the batch,
so it is recorded here rather than mentioned in passing.

### The symptom

```
git commit  ->  fatal: this operation must be run in a work tree
git status  ->  fatal: this operation must be run in a work tree
git rev-parse --is-inside-work-tree  ->  false
git config --get core.bare           ->  true
```

**`.git/config` line 4 read `bare = true`** in a clone that has a full working
tree. Every `add`, `commit` and `status` failed; `git log` still worked, which is
why HEAD read normally and the failure looked like a commit-message problem.

### The fix, and it is one line

```
git config core.bare false
```

**Nothing was lost.** HEAD was unchanged at `5b5b2963`, both new documents were
still present as untracked, and no commit had half-applied.

### WHAT CAUSED IT IS NOT ESTABLISHED, AND I AM NOT GUESSING

**No tool in `tools/`, `tests/` or `.githooks/` sets `core.bare`** — grepped,
zero hits. So it was not set deliberately by anything in this repo.

What IS measurable is the condition it happened under: **28 worktrees are
registered in `.git/worktrees` and their directories are all still present in
`%TEMP%`.**

| prefix | count | likely source |
|---|---|---|
| `sairn-abl-*` | **7** | an ablation harness |
| `gate12-*`, `gate-probe*` | 5 | push-gate probes |
| `sairn-sab-*` | 2 | a sabotage probe |
| `defreg-probe*`, `defreg-vocab` | 3 | defect-register probes |
| `condcov-*` | 2 | condition-coverage |
| `check4-probe`, `check8-probe`, `newchk`, `invis-flag`, `reseat-probe`, `wt_c9`, `tmp.*`, `sairn-gate-base-*` | 9 | assorted |
| **`drs-sandbox-*`** | **0** | **none are mine** — `dead_rule_sweep.py` reaps its own by name on the way in and out |

**That accumulation is the standing hygiene problem and it is platform-wide, not
mine.** Whether it caused the flip is undetermined; that 28 stale registrations
exist at all is not.

### What I did NOT do

**I did not prune them.** `git worktree prune` only forgets entries whose
directory is gone, and every one of these directories still exists — so pruning
would do nothing, and *removing* 28 other sessions' worktrees is not a call I
get to make from inside a batch. **Reported, not swept.**

**NEXT ACTION for whoever owns worktree hygiene:** decide whether a probe may
leave a registered worktree behind at all. `dead_rule_sweep.py` already answers
no for its own, by name, and that pattern is the one to copy.
