# cody b33 — the inverted-projection sweep, and what "b29's eight defects" actually are

## 1. The concept, stated before the scan

In `Object.assign(a, b)` the **later** source wins. A projection that lists the
authoritative columns **first** and a stored or client-supplied blob **last**
lets the blob override the server's value. The scan finds every keyed object
literal that precedes a non-literal source; **each hit is then classified by
hand** — LIVE only if the blob can actually carry that key, INERT if the write
path allowlists or strips it. The scan reports shape, never intent.

Tools (committed, `docs/b33-sweep/`):

- `projection_order_scan.py` — comment/string-masked bracket matcher; also
  finds `{ key: v, ...blob }` object spreads. **10 synthetic fixtures lock the
  criteria and the scan refuses to run if they fail** (both directions: inverted,
  safe, all-literal, string/comment-contained, nested calls, empty literal).
- `strip_cross.py <dir> <file.js>` — for each hit, compares the literal's keys
  to every `storedBlob(…, [list])` within ±260 lines.

Fix at each: columns/stamped fields applied **last**. `api/b33-projection-order-sweep.test.js`
(12 arms) plants a forged copy in each and asserts the server's value comes back;
**ablating all four flips turns A1, B1, C1, D1 and S1 red (7 pass / 5 fail)**.

### What was NOT swept, and why

- `*.html` clients. A client projection is not a trust boundary.
- The ~50 heuristic sites above. A runtime differential per resource would prove
  them; it was not run.
- Sites that build the merge in two statements (`const out = {…}; Object.assign(out, blob)`)
  — the scan keys on the call's first argument being a literal.
