MEASURED IN THE ORDER THAT MAKES A GREEN ARM MEAN ANYTHING. The race is
probabilistic, so an arm written after a fix can be passing because the race
never fired. Driven against the UNPATCHED function first:

    unpatched  2 writers + 1 tight reader, 400 saves : 335 PermissionError
               -> ARM 1 FAILED, and ARM 3b FAILED (no retry existed at all)
    patched    2 writers, 400 saves                  : 0, 0, 0 over three runs
    patched    2 writers + 1 tight reader, 400 saves : 4, 12, 4 over three runs

BOTH PATCHED NUMBERS ARE REPORTED AND THAT IS NOT HEDGING. The reader in phase B
reopens the destination in a tight loop and holds it open far more of the time
than any real caller, and it CAN starve a bounded retry. Phase A is the routed
scenario -- two sessions calling --open or --discharge -- and it is zero. Phase B
is disclosed under a stated 5% ceiling (<=20 of 400) with the unpatched 335
beside it. One combined figure here would be the fabricated half of a two-number
result, which is the second cross-domain discipline.

THE SHAPE OF THE FIX, and each property was separately earned:
  * PermissionError BY NAME. `except OSError` would also catch a full disk and a
    vanished directory, and retrying those 20 times then raising is strictly
    worse than raising once. ARM 4 drives OSError(ENOSPC) and asserts it escapes
    on the FIRST attempt -- measured (1, True, False).
  * IT RE-RAISES ON EXHAUSTION. A retry that gives up quietly converts a lost
    record into a SILENT lost record. ARM 3 stubs os.replace to fail forever and
    asserts PermissionError is raised; ARM 3d asserts the temp file is still
    cleaned up, so docs/ does not fill with orphans.
  * THE CAP IS A DECISION. 20 attempts at the measured ~76% per-attempt failure
    rate puts exhaustion near 1e-11, so an exhaustion is a signal. UNBOUNDED IS
    WRONG -- it turns a deadlock into a hang, which PR 1.12 names as the shape
    that must never exist. ARM 3c asserts the retry count is bounded.
  * SAFETY WAS ALREADY FINE AND MUST STAY FINE. ARM 2 runs a reader racing both
    writers and asserts it NEVER sees an unparseable file -- 0 across every run.
    A retry that fixed liveness by widening the write window would pass ARM 1
    and break the property the atomic write exists for.

THE ROUTED DOC'S OWN PREDICTION HELD, AND IT IS THE INDEPENDENT CHECK:
tests/run_tier_a_review_gate_probe.py now prints "RETRY COUNT: save_reviews
needed 0 retry/retries to get BOTH writers through" and ALL ARMS PASS. Arm 12's
expected answer is still 1 -- only the write is retried; the read-modify-write
race where two --open calls lose a record is untouched and still disclosed.

WHAT IS NOT COVERED: POSIX. The retry branch is unreachable there, so this
