### Item 3 — the IOLTA attestation. **BUILT.**

> **CONCEPT, STATED BEFORE ANY CODE.** A completed three-way reconciliation
> becomes an ATTESTED record only when a bar-admitted person signs a hash of the
> exact comparison that was run; a firm with **exactly one** active
> owner/attorney may switch on a per-firm single-signer setting and attest
> alone, and every attestation taken that way is stored as
> **`signer_mode: 'single'`** — so the record never claims two people looked
> when one did.

Michael's answer to **§6** of the b21 design, a hybrid of its answers (2) and
(3). Neither half stands alone: (2) alone is the policy table SAIRNlaw's own
countersign schema already refused once; (3) alone leaves a solo attorney no
route.

**TWO ENFORCEMENT POINTS, AND THE SECOND IS THE ONE THAT MATTERS.** `set_policy`
refuses to switch it on for a firm with two bar-admitted employees; **`attest`
RE-COUNTS the roster every time**, so a firm that opted in as a solo and later
hired a second attorney loses the route without anyone touching the setting. A
check that runs only at set time is an authorisation that outlives its own
precondition. **The count fails CLOSED** — `null` is 503 `ELIGIBILITY_UNKNOWN`,
never "one, so go ahead".

**`api/_lib/countersign.js` IS NOT WEAKENED.** Its header states it has no policy
table, no `set_policy`, and **no self-signature, ever**. The single-signer path
does not touch the countersignature token at all; a solo attestation is a
**different kind of record**, not the same record with a check switched off. Arm
F3 shows the shared lock still refusing a self-countersignature.

**A SECOND PROFILE, NOT A WIDER ONE — and that is a constraint, not taste.**
`api/law-countersign.js` carries ONE `preparerRoles`, `{ paralegal }`, so adding
`law_trust_attestation` there would have meant **only a paralegal could prepare
an attestation and an attorney could not**, and widening the list would have
changed C2's decided answer as a side effect. **Arm E3 of
`api/b18-countersign-lock.test.js` therefore STAYED GREEN** where the design note
predicted it would need re-aiming — b18 re-run 59/0.

**The token table is REUSED, measured not assumed:**
`sairnlaw_countersign_tokens.resource` is `text not null` with **no CHECK on its
value**, and that schema is already run — so the two-signer path needs **no new
SQL**. Only the record table is new.

**`sql/sairnlaw_trust_attestations.sql`** — the digest gives only the path, per
the dispatch. Its self-signature CHECK is **conditional on `signer_mode`, in both
directions** (`dual` ⇒ two names, `single` ⇒ one), so a row cannot be a
self-signature without admitting it and cannot claim to be solo while naming two
people. Grants are **SELECT + INSERT, no UPDATE, no DELETE**, behind a leading
`revoke all`. Four negative inserts **and a positive control**, because four
erroring inserts are equally consistent with *"the constraints work"* and *"this
table rejects everything"*.
