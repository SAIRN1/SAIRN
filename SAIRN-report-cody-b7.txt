6. ITEM 4 -- THE PREMISE WAS WRONG, THE DAMAGE WAS REAL, AND IT IS NOW REFUSED
================================================================================

6.1 THE PREMISE, MEASURED BEFORE ANYTHING WAS BUILT

The brief said the worktree probes corrupt .git/config. THEY DO NOT. Measured in
a throwaway repo on this git version: `git worktree add -q --detach` leaves
.git/config BYTE-IDENTICAL -- same sha, same 168 bytes -- and creates
.git/worktrees/<name>; `worktree remove` removes it again. Probe arm 7 PINS that
measurement so the original wording cannot creep back, and it is written to fail
loudly if a future git version changes the answer.

6.2 BUT THE DAMAGE IS REAL, AND I REPRODUCED IT BY ACCIDENT

A bare `python tools/guard_ablation.py --help` created
.git/worktrees/sairn-abl-8c6o2uub IN THIS CLONE and, when the run was killed,
LEFT IT THERE. git status never showed it. `git worktree prune` would not take
it while its temp directory survived -- it took removing the temp directory
first, then pruning. And a stale entry makes the NEXT `worktree add` refuse, so
one dead probe blocks an unrelated run in a directory nothing displays. That is
hank's WRITES(SHARED) finding, reproduced live, with residue I had to clean by
hand.

6.3 THE GUARD

tools/git_config_isolation.py -- `python tools/git_config_isolation.py --
<command>`. Snapshots .git/config bytes and the .git/worktrees listing, runs the
command with GIT_CONFIG_GLOBAL and GIT_CONFIG_SYSTEM pointed at throwaway files
and GIT_CONFIG_NOSYSTEM=1, then compares and RESTORES. A guard that only reports
is a notification; this one puts the bytes back and then re-reads to confirm.

  exit 0  ran, live git state unchanged
  exit 1  CHANGED -- restored, and A FINDING ABOUT THE COMMAND whatever the
          command itself returned
  exit 2  COULD NOT RUN -- no command, not a clone, or the snapshot failed
  exit 3  the command could not be started

Exit codes deliberately distinct from the wrapped command's, because folding
them is how "the probe passed" gets read off a guard's zero.

6.4 ADOPTED, NOT JUST OFFERED

condition_coverage.py, dead_rule_sweep.py and guard_ablation.py now call
require_isolation() before their `worktree add`. A bare live run exits 2 with
the one-command fix printed; under the guard they proceed unchanged.

OTHER SESSIONS WILL SEE THIS, and it is in my status row rather than left as a
surprise. The refusal is scoped to the LIVE clone -- a tool driving a temp repo
is not the guard's business, and refusing that would make the guard the thing
that breaks selftests.

THE FIRST PLACEMENT WAS A REAL DEFECT, caught by running it rather than by
reading it: inserted above dead_rule_sweep.py's module docstring, the block made
