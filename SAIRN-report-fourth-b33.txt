3.1 ROUTING CODE EXISTS -- OFF-BRANCH

Commit 35169ea2, 2026-06-18, "Add maps-optimize and maps-static actions to
SAIRN Data Bridge for StoneDesk Field Map", adds 105 lines to api/bridge.js:

  * POST ?action=maps-optimize taking { addresses: string[] }
  * a call to Google's Route Matrix
    (routes.googleapis.com/distanceMatrix/v2:computeRouteMatrix) with
    travelMode 'DRIVE', keyed server-side so GOOGLE_MAPS_API_KEY never reaches
    the browser
  * a NEAREST-NEIGHBOUR ORDERING over the real drive-time matrix, starting at
    stop 0, with an explicit unreachable-pair fallback
  * a savedMinutes figure: as-given total minus optimised total
  * a sibling ?action=maps-static that fetches the preview image server-side
    and returns a data URL, so the key never appears in a browser-visible URL

Its own comment explains why it does NOT use Google's optimizeWaypointOrder:
that feature is gated behind a manual Support enablement request, and a
nearest-neighbour ordering over real drive times does not depend on a flag that
might not be turned on. That judgment is worth keeping.

IT IS NOT ON main AND NEVER HAS BEEN:

Written AFTER section 3 had a real answer, which is the sequencing b32 got
right and was interrupted inside. SCOPE ONLY; no app code was written.

SHAPE: one shared module under api/_lib/, called by api/sd-data.js's existing
resource dispatch as resource 'routes'. NOT a new top-level endpoint and NOT
api/bridge.js -- whose own header says it is StoneDesk-only and explicitly is
not the cross-app data path other apps mean, has no read side, and answers 405
to GET.

SCHEMA: rt_routes + rt_stops. Four decisions that are the point, not decoration:

  * saved_seconds is NULLABLE and NULL means NOT COMPUTED. The archived
    implementation floored it at Math.max(0, ...), which makes "we could not
    tell" and "we saved nothing" the same value on screen. They are different
    facts and the column keeps them different.
  * optimized_at NULL means never optimised; `source` says which basis.
  * lat/lng nullable, NEVER 0,0. Null Island is a real failure mode, and
    sairnsenior already has the right instinct.
  * a `locked` flag, because a real day has fixed appointments and an optimiser
    that reorders a 9 AM commitment is worse than no optimiser.

API SURFACE: read / upsert / reorder / optimize. optimize must answer in three
states and never fold them: basis 'drive-matrix' (a real matrix answer),
basis 'unavailable' (no key, no reach, or an unreachable pair -- THE STORED
ORDER DOES NOT CHANGE and saved_seconds stays NULL), and it NEVER returns a
reordering it did not compute. Auth is licence + session, not licence-only: an
address list joined to a named employee is not shop metadata.

FIRST APP: STONEDESK. Not because it is biggest -- because its client half
already exists and is currently broken. fmRunOptimize() already builds the
address list, already consumes {order, savedMinutes}, already persists into
sdFieldOrder, already re-renders, and already splits done from not-done
(stonedesk.html:12920-12923). Phase 1 there is three edits, not a feature.

SECOND APP, argued: SAIRNGROUNDS, because it already owns the only real
gcdHaversineM() on the platform and the accuracy-band discipline around it.
When basis 'unavailable' fires, a straight-line ordering is a legitimate second
basis -- but only labelled basis 'great-circle' and never allowed to masquerade
as drive time. Grounds has the code and, more importantly, the habit.

EXPLICITLY NOT IN PHASE 1, said out loud so silence is not read as omission:
no geocoding, no live traffic, no time windows, no multi-day, no capacity
constraints, NO CREW ASSIGNMENT (phase 1 orders stops a human already
assigned; deciding WHO goes is a different problem with a different failure
mode), no new map rendering, and no per-app copy of the module ever.

7. A "TOOL BUG" I WAS ABOUT TO ROUTE TO cc -- AND IT WAS MY READING ERROR
================================================================================

THIS SECTION SAID tools/context_verify.py OVERSTATED THIS SESSION'S CONTEXT BY
FIVE TIMES AND ROUTED IT TO cc AS A DEFECT. THAT WAS WRONG. The context-digest
push gate refused the push and that refusal is what exposed it. The correction
is more useful than the claim would have been, so it is kept rather than
quietly deleted.

WHAT HAPPENED. An early run printed:

  agent     REAL %       prompt      window   age h
  fourth     94.2%      188,338     200,000     0.0

I read 94.2% as the tool's answer, concluded it had inferred a 200,000 window
for a 1,000,000-token session, and wrote it up as a five-fold overstatement.

THE TOOL HAD ALREADY SAID OTHERWISE AND I DID NOT READ IT. --agent sets an
`ambiguous` flag whenever more than one published window still fits the
observed maximum (tools/context_verify.py:437-456). At 188,338 tokens BOTH
200,000 AND 1,000,000 FIT, so the row was flagged and carried a `why` naming
both candidate percentages and the fix -- "Declare it once: python
tools/context_verify.py --provision-window <tokens>". The file says the same
thing in its own header at lines 76-89: THE INFERENCE IS A FLOOR, THEREFORE THE
PERCENTAGE IS A CEILING. b21 built that guard on purpose.

I TRUNCATED THE OUTPUT WITH `tail -20` AND QUOTED THE NUMBER WITHOUT THE
WARNING ATTACHED TO IT. That is the exact failure CLAUDE.md names -- a
truncated read is indistinguishable from a complete one -- committed while
writing up a different session's measurement discipline.

NOTHING IS WRONG WITH THE TOOL AND NOTHING IS ROUTED TO cc. Later in the same
session the prompt passed 200,000, only one published size still fit, and it
resolved correctly and unprompted:

  fourth     30.9%      308,588   1,000,000     0.0   [window INFERRED]

THE ONE THING GENUINELY WORTH CARRYING FORWARD is not a defect report, it is a
usage rule: --digest-line is the command, its output is pasted verbatim, and
the context-digest push gate refuses anything hand-written -- which is
precisely how this got caught. A figure read out of a truncated table is not a
measurement even when the tool that produced it is correct.
