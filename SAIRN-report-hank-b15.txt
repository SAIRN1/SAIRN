2. THE ONE LEGACY STEDI CIPHERTEXT -- THE STEP, AND IT IS NOT SQL
--------------------------------------------------------------------------

Michael's census result: sc_credentials legacy_rows = 1, the MFA table clean,
and SD_AUTH_SECRET_PREVIOUS must not be cleared until that row is v2.

THE CIPHERTEXT CANNOT BE RE-ENCRYPTED IN POSTGRES, and the reason is the whole
deliverable. The key never leaves the Node process: api/_lib/auth.js:874
derives AES-256-GCM from sha256(SD_ENCRYPTION_KEY), and Postgres has neither
the key nor the function. AN UPDATE THAT PUT ANYTHING INTO
data->'stedi'->>'enc' WOULD WRITE A VALUE NO READER CAN DECRYPT WHILE
SATISFYING THE CENSUS -- it would stop matching "not like 'v2.%'", the census
would report ZERO, and that zero would AUTHORISE clearing the old key over a
credential nobody can read. The file says do not write SQL for this, with that
reasoning.

THE STEP: a Compliance Admin re-saves the SAME Stedi key in SAIRNcode's
eligibility panel (sairncode.html:6068 posts action:'set', service:'stedi'),
which goes through api/sc-credentials.js:200-205, which calls encryptSecret(),
which writes the v2. prefix because SD_ENCRYPTION_KEY is set in production. No
new code, no hand-edited ciphertext. THE LAST-4 FINGERPRINT IS COMPARED BEFORE
AND AFTER so a wrong key cannot be substituted silently, and updated_at must
move or the write did not land. Then census PART 1 -> legacy_rows = 0.

AND IT SAYS WHAT TO DO IF THE PLAINTEXT IS NOT TO HAND: STOP. A server-side
re-wrap is possible in principle -- the legacy value is still readable, which
is the only reason eligibility works today -- but it is new code handling a
decrypted secret, it must REFUSE when decryptSecret() returns null (otherwise
it writes the ciphertext of an empty string and takes the census green over a
destroyed credential), and it needs an independent review. I DID NOT BUILD IT.
Routed as a decision.
