1. ITEM 1 -- THE RETRY LOOP RECOMMITTED THE GATE'S WRITE-BACK
================================================================================

THE ONE-LINE CONCEPT, stated before the code: the gate's write-back is
bookkeeping ABOUT the commits being pushed, so it gets ONE bookkeeping commit
that every later round AMENDS -- never a new commit per round, and never folded
into a work commit, because a work commit's sha IS the row key and amending it
would orphan the row the gate just wrote.

tools/push_retry.py already amended generated documents but had no arm for
docs/scrutiny-flags.json, so the loop that replaces the hand-written one
inherited the defect. fold_scrutiny() now runs at the top of every --loop
attempt. First round: creates "chore(gate-bookkeeping <tip7>): ..." and
registers its subject with the amend guard. Later rounds: amend, with a pathspec
so nothing else staged is swept in. It folds ONLY a provable append (every
HEAD row survives unchanged; no other top-level key moved); anything else is
named and not staged.

DRIVEN LIVE, not just selftested: the real loop made exactly one bookkeeping
commit across four refused attempts in this batch (git log showed 3 commits
ahead -- work, handoff, one bookkeeping -- not 3 + N), and the rows stayed
stable across amends because the keys are the work commits' shas.

Selftest arms run on a real scratch repo, because the defect was a commit
COUNT. Two ablations: replacing --amend with a plain commit turns "round 2
AMENDS it" red; removing the published-HEAD check (section 7) turns the
published arm red.
