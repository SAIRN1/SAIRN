ITEM 3 -- A LOCK THAT CRASHES IS NOT A LOCK THAT PASSED
================================================================================

FOUND BY THIS BATCH'S OWN BROKEN ARM, which is the only reason it was found. A
NameError in one of item 1's new arms printed 23 of 50 arms, no summary line,
and EXITED 0. `--selftest` and `--preflight` were dispatched from INSIDE the
hook's `except Exception: sys.exit(0)` -- fail-open, which is CORRECT for the
gate path, because a gate that crashes closed gets disabled and then protects
nothing, and WRONG for the criteria lock. A caller reading the exit code saw a
clean lock over a selftest that never finished: PR 1.11's third state in the
most load-bearing place on the platform.

  0  the lock ran and passed
  1  the lock ran and FOUND something
  2  the lock COULD NOT RUN -- a third state, not a pass

Lock entry points now run under _locked_entry, OUTSIDE the fail-open try.
ARMS, driven through the real seam rather than asserted:
  * a lock returning 0 or 1 keeps it -- the policy touches neither;
  * a lock that RAISES is exit 2, with the traceback;
  * a SystemExit passes straight through unchanged (exit 7 in, 7 out);
  * ABLATION, the pre-fix policy returning 0 for the same crashing lock;
  * ABLATION CONTROL, the pre-fix policy was RIGHT about pass and fail -- it
    only ever lied about the crash;
  * WIRING, a text read of this file's own __main__, with its limit stated
    rather than hidden: it cannot prove behaviour, only notice the two lines
    swapping back, which is how the defect arrived.

END TO END, through __main__, which the in-process arm cannot reach --
docs/2026-10-17-cc-b17-locked-entry-crash-injection.py takes the real hook,
injects `raise RuntimeError` as selftest()'s first line, writes two copies with
the two wirings and runs each as a subprocess:

THE SWEEP FOR THE SAME SHAPE ELSEWHERE, AND ITS OWN FAILURE FIRST. A probe
