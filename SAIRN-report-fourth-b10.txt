5. ITEM 5 -- THE PROCEDURE, AND THE NUMBERING DISCIPLINE

Written into docs/METHODOLOGY.md, 146 lines, two sections.

THE PROCEDURE, six steps, for a refusal that hides several defects:
  1  read the message as a SYMPTOM and grep for the line that printed it. b9's
     "the outgoing range A..B could not be read" came from
     register_feed_gate.py:747, not from the push gate everyone assumed.
  2  drive the gate DIRECTLY before changing anything -- every pre-push gate
     here reads ref lines on stdin, so none needs a push. A dry run costs
     minutes; a push costs a race.
  3  ESTABLISH THE COUNT BEFORE FIXING ANYTHING. This is the step b9 was
     missing. Run every gate in the hook and record each exit code rather than
     stopping where the hook stops, then ask what the refusal does NOT prove.
     b9's generator refuses on its FIRST empty derivation source, so the
     refusal REPLACED the finding. A refusal can MASK a finding, not merely
     precede it.
  4  for each cause, ask where the SUBJECT came from. Three of b9's four were
     one value read by three programs; fixing it per-gate moved the refusal
     along twice before anybody fixed it where it entered.
  5  record each cause SEPARATELY with its own injection commit. One record
     saying "the push was blocked" would have lost the fact that one of the
     four was a false finding whose remedy instructed a land grab.
  6  re-derive every figure at finalisation. Three rebases ran during b9.

  THE TRAP, NAMED: when fixing gate N reveals gate N+1 the symptom is a SECOND
  refusal, and the honest reading is progress rather than failure. b9 hit it
  three times. What makes it readable is that all three fixed gates now PRINT
  their own name and what they substituted.

  THE COROLLARY: not every refusal is a defect. One b9 attempt was refused for
  being issued inside a shell wrapper, and the gate's own message said "ISSUE
  THE PUSH DIRECTLY -- there is nothing wrong with the change." It was right.
  Step 1 includes believing the message when it says the change is fine.

  WHAT IT DOES NOT DO, said in the document: it does not find the defects. It
  stops a session reporting one cause when there were four. Nothing in it is
  mechanised, and step 3 is a habit rather than a tool -- the first time
  somebody skips it, the procedure buys nothing.

NEXT FREE NUMBERING, four rules, so two sessions cannot route the same number:
  1  never quote the number -- COUNT THE HEADINGS at the HEAD you are on, with
     a snippet that reports GAPS AND DUPLICATES as well as the maximum, because
     those are the two ways a count can be confidently wrong.
  2  a routed rule carries NO NUMBER. It carries its text, its evidence, and
     "NEXT FREE is N as of <sha>". The number is assigned by the intake at the
     moment the heading is written, which is the only moment the count is true.
     That is what makes a collision structurally impossible rather than
     unlikely.
  3  do not number a rule in a file you hold under claim. A session holding the
     conventions document can always find a free number, so "it was free" stops
     being evidence of anything.
  4  when the intake assigns a number, record the COUNT in the commit, not the
     number alone. "Added convention 35" is unfalsifiable a week later; "34
     headings, 1->34, no gap, no dup, so 35" can be re-derived by anybody.

  THE COLLISION IS NOT HYPOTHETICAL: on 2026-09-25 two sessions each added an
  eleventh convention within the hour.

  RE-COUNTED AT THIS HEAD by that method, not quoted: 34 headings, 1 -> 34, no
  gap, no duplicate, NEXT FREE 35. NO RULE IN THIS BATCH WAS GIVEN A NUMBER,
  and rule 3 is why.

  OPEN AND STATED: nothing mechanises rule 1. No check counts those headings or
  refuses a duplicate or a gap, so it holds only while sessions run the snippet
  by hand -- which is the exact shape of the eighth discipline, about checks
  that stop testing anything. Nobody owns the conventions file, so it is a
  routed observation and not a plan.
