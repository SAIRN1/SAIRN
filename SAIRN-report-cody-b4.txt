7. ITEM 5 -- THE PROBE PAIR: MECHANISM VERIFIED, VERDICTS COULD NOT RUN
================================================================================

7.1 THE DEFECT, AND IT IS REPRODUCED RATHER THAN ASSUMED

tests/push_gate/check4_probe.py and check7_probe.py planted fixtures in a linked
`git worktree add --detach`. A linked worktree SHARES .git/config with the clone
that owns it, so a `git config` write made by ANYTHING running with cwd inside
the worktree lands in the REAL clone's config.

The reproduction is two commands, recorded in
docs/2026-10-07-fourth-routed-pinned-worktree-shared-config.md:

  git worktree add -q --detach /tmp/repro HEAD
  git -C /tmp/repro config core.bare true

left `bare = true` in Documents/SAIRN-fourth/.git/config, after which EVERY git
command in that clone failed with "fatal: this operation must be run in a work
tree". check8_probe.py made exactly this move on 2026-10-06 (b23dbc2e); these
two are the pair that document named alongside it and never got it.

7.2 HARDLINKED, NOT --no-hardlinks, AND THE DEVIATION IS MEASURED

The brief asked for `git clone --local --no-hardlinks`. Measured in this clone
on 2026-10-12: .git is 100MB; `--no-hardlinks` took 7.7 seconds and left 207MB
on disk. The hardlinked form costs no measurable time and no disk, which is why
check8_probe.py uses it and says so.

These probes run in the whole-tree suite, in four clones, after every push.
`--no-hardlinks` buys object-store isolation nothing here needs: git never
rewrites a pack in place, new objects land in new files, and no probe runs `gc`.
The config was the whole defect and a clone removes it either way. Said out loud
in the code, in the commit and here, because it is a deliberate deviation from
an instruction rather than an oversight.

7.3 THREE THINGS A CLONE DOES NOT INHERIT, EACH A SILENT-PASS DIRECTION

  core.hooksPath   CONFIG, not a tracked file. Without it the pre-push hook
                   NEVER FIRES and the probe reports "not blocked" about a gate
                   it never asked. Set explicitly, and _setup_clone() refuses if
                   .githooks/pre-push is absent from the clone.
  origin           In a clone of a local path it points at THAT PATH. Pushing
                   there exercises a different thing. The real URL is read off
                   MAIN.
  the retry fetch  dry_push() said `git -C MAIN fetch` and worked ONLY because a
                   worktree shares MAIN's object store. It now fetches into the
                   clone. Left unchanged it would have fetched the wrong
                   repository and the retry would have failed exactly as the
                   first attempt did -- which reads as "the check did not fire".

_setup_clone() returns a REASON string and the caller exits 3 rather than
limping on.
