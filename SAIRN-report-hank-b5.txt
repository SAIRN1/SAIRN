THE DESIGN'S ACTUAL CONTRIBUTION IS THAT THE THREE GUARDS ARE THREE DIFFERENT
KINDS OF RULE, which decides where each belongs:

  activeProvisioners()  a DERIVED READ. Nothing to enforce; it is the input to
                        the other two. Needs no endpoint and no column.
  SPEC 1c               a WHOLE-TABLE INVARIANT. "At least one active
                        provisioner, or zero officers" is a property of the
                        SET, so a per-row handler cannot evaluate it without
                        reading the rest of the table. -> THE HANDLER.
  sole-holder           a UNIQUENESS CONSTRAINT in disguise. -> A PARTIAL
                        UNIQUE INDEX, because a read-then-write loses to two
                        concurrent writes, and an outgoing plus an incoming
                        Commander is exactly that race.

SHIPPING BOTH AS HANDLER CODE WOULD PUT A SET-INVARIANT AND A UNIQUENESS RULE
IN ONE `if` BLOCK, which is how one of them ends up only approximately
enforced. That is the point of the document.

THE INDEX'S COST IS STATED RATHER THAN BURIED: it puts the capability list in
TWO places -- CAPABILITIES in the page and the index predicate in SQL -- which
is the two-lists-that-must-agree shape this platform keeps paying for. SO THE
RECOMMENDATION IS WORSE THAN THE STATUS QUO WITHOUT a test asserting the
predicate names exactly the `sole:true` ids.

THREE THINGS THAT WILL GO WRONG IF THE HANDLER HALF IS WRITTEN CARELESSLY, all
in the document: the write is an UPSERT so the invariant must be computed
against the MERGED roster and not the payload; the pre-read must fail CLOSED;
and ZERO OFFICERS IS A SAFE END STATE that must stay writable, or a post trying
to start over is bricked by the guard meant to prevent exactly that.

ORDER: INVARIANT AND UNIQUENESS FIRST, ROLE RESTRICTION SECOND. They are
independent, and both hold whichever roles end up allowed to write -- a
Commander can deactivate the last provisioner as easily as anyone. So the two
guards are NOT blocked on Michael's role-matrix answer.

THE CLIENT GUARDS SHOULD STAY. They give an immediate specific refusal with the
post's own org-type title in it; the server gives a 409 a page has to
translate. Removing them would make a correct refusal read as a server error.
