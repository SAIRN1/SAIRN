THE WINDOW INFERENCE IS A FLOOR AND b20 DID NOT SAY SO. Pointed at a fresh
session for the first time, the tool reported cc at 70.9% of 200,000 over

the file is my own echoed command output. There is no window field, and the

THE FIX: THE DENOMINATOR GETS A DECLARED SOURCE AND THE INFERENCE BECOMES THE
FALLBACK.

    python tools/context_verify.py --provision-window 1000000

writes .git/sairn-context-window -- untracked, per-clone, surviving a rename,
the convention tools/sairn_session_identity.py already uses and which this
sits beside.

IT IS KEYED BY SESSION ID, NOT BY CLONE, AND THAT IS NOT TIDINESS. The
observed prompt witnesses a declaration that is too SMALL, and that case is
refused naming the declaration as the wrong thing. NOTHING witnesses one that
is too LARGE: 1,000,000 left standing in a clone whose next session ran on a
200k model would report 15% while that session sat at 75% -- which is the
understatement b20 existed to stop. So a declaration speaks only for the
session that made it and a new session declares again. One command per batch.

AND WITH NOTHING DECLARED AND MORE THAN ONE WINDOW STILL FITTING, THE ROW IS
AMBIGUOUS: the token count is reported, both candidate percentages are named,
and --digest-line REFUSES to emit a confident line. A 5x-wrong denominator
wired into every digest is worse than a digest that says it does not know.

MEASURED RIGHT NOW, and it is the live demonstration: hank 72.8% of 1M and
