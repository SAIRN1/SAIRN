1. ITEM 4 FIRST, BECAUSE IT IS A DEPARTURE FROM THE INSTRUCTION
================================================================================

THE INSTRUCTION WAS AN APPS PROFILE PER APP. I DID NOT BUILD SIXTEEN PROFILES.

The profile plan was mine -- it was b29's own NEXT line -- and it does not
survive contact with the platform. Surveyed rather than assumed, across the
seventeen root products:

    SEVEN   have no #gkey licence gate
    FIVE    have no nav() panel switcher
    THREE   have no panel-* elements at all

A rendered profile needs all of those PLUS playwright, a chromium binary,
network reach, a live Supabase and a demo PIN. Wired into a gate, that exits
2 COULD NOT RUN on most of the platform -- and under this repo's fail-closed
rule COULD NOT RUN means DENY. Every push from a clone without a browser would
have been blocked by a check about button colours.

So the sixteen apps were measured with a STATIC half that reads the file and
needs nothing, and that same half is what went into the gate. The coverage
this gives up is stated in the gate's own comment rather than absorbed
quietly, and it is quantified in section 5.

2. ITEM 3 -- THE GATE
================================================================================

CHECK 5b in tools/sairn_push_gate_hook.py. It runs on any push that CHANGES
HTML -- the same trigger the reachability check already uses -- so an ordinary
push costs nothing.

TWO CLASSES, BOTH SOUND WITHOUT A DOM:

  A  a CSS rule or a style="" ATTRIBUTE declaring both a colour and an OPAQUE
     background below WCAG 2.2 AA. This is where the worst of b29 lived:
     .bp at 2.77:1 was every primary button in SAIRNdental and .sb.on at
     3.57:1 was every active sidebar row.

  B  a var(--token) defined nowhere with no fallback. This one is not a style
     question. An unresolvable custom property makes the whole declaration
     invalid at computed-value time, so the property is DROPPED rather than
     falling back -- b28 shipped border-left:3px solid var(--accent) and the
     stripe rendered at 0px, with 22 passing unit arms behind it.

THE FIRST DRAFT READ <style> BLOCKS ONLY, AND RUNNING IT AGAINST THE KNOWN-BAD
BYTES IS WHAT SAID SO. Against the exact file b29 repaired it reported five
real contrast failures and NOT the undefined var(--accent) -- because that one
sits in a style attribute on a div. A gate that misses the defect it was built
from is worth nothing. Inline attributes are parsed now, and a fixture asserts
that element by name:

    inline <div#pc-edit-banner>   undefined var(--accent) in `border-left`

ABLATION OF THE GATE ITSELF -- through the REAL --pre-push hook in an isolated
worktree, three commits differing by one line each:

  ARM A  an HTML comment, no style change
         -> NO contrast block. (The push was blocked by an unrelated
            derived-docs gate, which is a different check.)
  ARM B  .b30gateprobe{background:#0EA5E9;color:#fff;font-size:13px}
         -> Blocked: "2.77:1 (need 4.5)  #fff on #0EA5E9", NEW FINDINGS: 1
  ARM C  border-left:3px solid var(--b30nosuchtoken)
         -> Blocked: "undefined var(--b30nosuchtoken) in `border-left`"

ARM A'S SILENCE ONLY MEANS SOMETHING BECAUSE B AND C FIRED ON THE SAME PATH.
That is why the ablation was run against the hook rather than against the
checker.

FAIL-CLOSED IS UNCHANGED: a missing checker DENIES, exit 2 from the checker
DENIES, an exception DENIES. Skippable as `contrast` through gate_skip (nine
ids now), which requires a written reason -- deliberately not in the
unskippable three, because a new gate's first false positive should cost one
scoped skip rather than a blanket one.

AND ONE THING THE PUSH ITSELF TOLD ME, NOT HIDDEN: the gate's own check-10
freshness notice fired -- "the push gate that just ran is NOT the one on
origin/main". That is expected for a push whose subject IS the gate. MY NEW
CHECK DID NOT GATE MY OWN PUSH. It gates every push after it, and the ablation
is what stands in for that until the next session's push exercises it.

THE PATTERN IS THE HOUSE PATTERN, NOT SIXTEEN UNRELATED BUGS. Nearly every
app's .gbtn and .bp is white text on that app's own brand colour:

  sairnmechanical 1.98:1   sairnbuild 2.15:1   sairnscape 2.28:1

One design decision, repeated seventeen times.

AND IT FOUND ONE b29 MISSED, IN THE APP b29 FIXED. .gbtn -- the Activate and
Sign In buttons -- was still white on #0EA5E9 at 2.77:1. The rendered sweep
could never have found it: those two screens come BEFORE sign-in and it only
ever visits signed-in panels. NEITHER HALF OF THIS TOOL WOULD HAVE CAUGHT IT
ALONE. Fixed to --pd and verified on the live deployment at rgb(3,105,161) on
both screens.

WHY IT LANDED AS A RATCHET RATHER THAN A CLIFF. A gate denying on any finding
in a changed file would have blocked every push touching FOURTEEN apps on the
day it landed. This platform already knows how that ends: 80 of the 94 rows in
docs/BYPASS-LOG.jsonl are an override taken because it was the only thing
available. So docs/wcag-contrast-baseline.json records the 153, the gate denies
only on findings NOT in it, and three things stop the baseline becoming an
amnesty:

  - every run PRINTS the outstanding debt per app, in front of whoever is
    pushing rather than in a file nobody opens;
  - the baseline grows ONLY by an explicit --baseline-write, which is a commit
    a reviewer can refuse;
  - the key is the FINDING, not the line number, so an unrelated edit
    thousands of lines above does not re-present old debt as new work -- and a
    SECOND copy of an accepted finding is still NEW, because adding another
    failing button where one already sat is a regression.

Ablated on a real baselined file: untouched stonedesk -> 87 accepted, 0 new,
exit 0. Same file plus one new rule -> 87 accepted, exactly 1 new, exit 1.

5. ITEM 6 -- CONVENTION 39, AND WHAT THE GATE DOES NOT CHECK
================================================================================

docs/2026-09-13-cross-domain-disciplines.md section 39:

  A CHECK IS WORTH WHERE IT RUNS -- choose the enforcement point by where it
  CAN run, and land a new gate with a BASELINE or it lands as a bypass.

Both halves were paid for by this batch before the gate ran once: the 7/5/3
survey that ruled out a rendered gate, and the 153 pre-existing findings that
ruled out a cliff. Denominator moved 38 -> 39, and the cannot-fire membership
question was asked and ANSWERED: 39 is NOT a member, because a rendered gate on
a browserless clone would have failed LOUDLY. Its failure mode is a gate people
route around, not a check that reads as coverage and silently cannot fire. The
THIRTEEN is untouched.

WHAT THE GATE CANNOT SEE, QUANTIFIED RATHER THAN HAND-WAVED: an
ancestor-dependent pair -- a rule with a colour and no background, or a
translucent background -- is reported UNRESOLVED and is NEVER folded into a
pass. Across the platform that is 4,439 UNRESOLVED, which is the majority of
every app's text. THAT NUMBER IS THE HONEST SIZE OF WHAT THIS GATE DOES NOT
CHECK, and guessing at it is precisely the mistake b29's rendered half made
when it read rgba(255,255,255,.15) over a blue bar as opaque white and
fabricated a 1.00.
